# Z62 首次 MENU 可用、退出报错与二次 MENU 拒绝分析

## 结论与范围

这不是“菜单画完一次就坏了”，而是原固件采集停止流程发生失败、记录错误状态，拍摄应用返回前台后显示该错误，并拒绝新的 MENU 请求。首次菜单请求排队时错误尚未记录，是首次与再次请求的重要区别。首次请求从许可检查到最终切换的完整无断点时序尚未捕获，不能把推导写成完整动态证明。

本轮是既有动态记录复核、原始固件静态反汇编和设备源码分析，**没有新启动 QEMU，没有修复设备，没有改固件/客体状态，也没有连接相机**。沿用[离线分析范围](../../analysis/z62-capture-diagnosis/scope.md)。flavor=null，severity=n/a_re。

样本：Z6II C1.70 完整主成员，SHA256 `bb83613121f843d65101da936d942acdc513d86dbd3abc26259d0d870d03f5d4`，基址 `0x10020000`。裸 ARM/Thumb 固件，不适用 PE 导入表；等价分析锚点为固定成员身份、原始指令、函数指针表、MMIO 和原有 QEMU RSP 记录。工具为本机 Python 3.12、Capstone 5.0.7；技能引用的共享 tool-index/precedent 文件不可用，未安装或启动额外工具。

## 1. 为什么第一次能开

自动菜单源码（本地证据，未分发：`<WORKSPACE>/third_party/z62-qemu/tools/z62_console.py:138`）只在应用管理器就绪、前台 index=3、虚拟时间至少3秒时排队 pin9 按下/释放；不是写应用索引或跳过原固件。

冷启动停止函数入口记录表明：
- foreground=`0305`：拍摄应用 APPLV。
- pending 原始字节=`00000200`，按小端解释为 `0x00020000`，不是 `0x200`：MENU 延后请求已经排队。
- status_codes=`[]`：此时尚无已记录状态码。
- 停止函数随后返回 `0x180`，事件9再把 `0x3F`加入状态列表；追加时 pending 仍为 `0x20000`。

另一个菜单态快照中，应用 index=1 与状态列表 `[63]` 同时存在。这证明**已进入的菜单可继续存在，并不要求采集错误列表为空**。原始菜单的显示/方向键链能工作，也不意味着帧采集、停流和恢复均已实现。

因此当前最有证据支持的解释是：首次请求先排队，停止/切换过程中才产生错误，已接受的请求仍进入菜单；返回拍摄后再发的新请求则碰到已经存在的错误。该解释由分次冷启动/菜单快照与静态代码交叉支持，尚缺一次连续追踪首次 gate→pending→stop→event49→应用切换的记录。不能断言固件存在“只允许一次菜单”的特殊规则。

## 2. 错误实际是什么

屏幕表现为原固件通用致命提示：`Error. Turn camera off and then on again.`。内部 `0x3F` 是状态代码，不是屏幕直接显示的字符串，也不是宿主 QEMU 的 Python 异常。

基线中的软件链为：

```text
采集停止调用 0x1026DB8A → 0x102DBB9C
  等待事件 0x800 失败 → 置返回位 0x80
  模式停止等待事件 0x20 失败 → 置返回位 0x100
  合并返回 0x180
通知分发 0x1026D434 → event9
映射/追加 0x103970D4 → 状态 0x3F
退出 MENU → APPLV 错误谓词返回1 → 显示 Error
新 MENU → 许可检查表项0x24 → 拒绝
```

| 失败 | 原始等待点 | 预期的事件来源 | 现有证据边界 |
|---|---|---|---|
| `0x80` | `0x102DBBAC`调用等待包装器；掩码`0x800`，参数100 | IRQ92 bit1；状态`0x20065508`、掩码`0x2006550C`；回调`0x102D7E52`置软件事件 | 返回0已记录；内核原始错误码未记录 |
| `0x100` | mode0停止`0x102DD9C8`内`0x102DD9FC`；掩码`0x20`，参数150 | sync组2 bit10；状态`0x20060044`、掩码`0x20060040`；`0x102D7F34/36`置软件事件 | mode停止返回`0x100`；时间单位未核定 |

包装器`0x1035D43A`将非零内核结果折叠为布尔0，因此准确说法是“等待失败”，不能仅凭0就认定为超时，不能把参数100/150直接写成毫秒。其余四个清理调用返回0，基线`0x180`的两部分有独立记录支持。

## 3. 为什么返回主界面才显示，随后按 MENU 无效

退出时`0x106316AC`断点仍为菜单 foreground=`0105`，状态已是`[63]`。切回 APPLV 后，`0x105B7E6C`读取 DSID `0x1921`，命中`0x3E..0x44`错误范围；在`0x10543034`观察到返回1。**退出主要暴露既存错误，并非必须在退出瞬间新制造错误。**

再次正常 pin9 输入在`0x106231C2`实际命中：R0=1，R4=`0x24`，状态`[63]`，pending=0。表项`0x1094DFDC`指向 Thumb 函数`0x105B7E6C`；谓词为真后执行`movs r5,#0`，返回不许可。

所以这次二次菜单失败不是浏览器吞键、LCD不刷新或单纯等得不够久，而是原固件主动阻止新请求。当前证据不足以证明 CPU 整体崩溃；旧菜单态四核 DFSR/IFSR 均为0，但那也不是对所有时刻都无异常的证明。

## 4. 对应 QEMU 的缺口与不能贸然采用的修复

传感器模型（本地证据，未分发：`<WORKSPACE>/third_party/z62-qemu/qemu/nikon-z62-sensor-config.c:149`）的帧完成响应依赖：frame-end上升沿、`laboratory-frame-completion`、mode2配置、IRQ92 bit1掩码。mode0完成响应依赖：显式写`0x20065504`、mode-enable、对应配置和`laboratory-mode-completion`。这两个实验开关默认关闭。基线缺少这两类完成响应，与原固件的两个等待失败一致。

帧时钟（本地证据，未分发：`<WORKSPACE>/third_party/z62-qemu/qemu/nikon-z72.c:1000`）发出sensor-frame-end，但帧同步使能撤销时会删除定时器。停止过程是否先关闭帧源、导致最后一个完成沿永远不来，是值得检查的时序候选，**未动态证明**。

已有三项完成组合及更完整握手组合仍未通过MENU往返，后续再次出现`0x3F`。因此：
- 不能把“打开两个实验开关”当成完整修复。
- 不能未经证实就周期性注入完成IRQ、放宽所有掩码或照搬Z72自动重臂。
- 不能靠清空状态列表、跳过gate或强制成功返回值验收。
- 真实24–200镜头、三星64GB卡没有接入本基线，当前证据不支持归咎于它们的兼容性；更不能声称两者已被完整仿真。

## 5. 本轮纠正：旧 event49 候选断点无效

旧报告将`0x10541790`当作 event49 consumer 候选；本轮重新核验原始字节：

```text
1054178E  e1f0ecfb  bl   #0x10622F6A
10541792  0120      movs r0, #1
...
105417E4  4920      movs r0, #0x49
105417E6  03a9      add  r1, sp, #0xc
105417E8  6af7aafc  bl   #0x104AC140
1054180A  eff04fff  bl   #0x106316AC
```

`0x10541790`位于32位Thumb BL的后半字，不是正常指令起点；它未命中不能支持“事件消费者没执行”。事件查询候选应从`0x105417E4/E8`观察，延后请求读取和应用切换在`0x10541802/0A`。这只是静态修正，尚未重新动态布点。已经实际命中的`0x106231C2`错误拒绝证据不受影响。

## 7. 下一步最小诊断

一次冷启动同时记录正确的gate、pending写入、两个内核等待的原始返回码、事件生产/清除及应用切换。重点同步记录IRQ92状态/掩码、sync bit10状态/掩码、mode写入、frame-sync使能与最后帧沿；再对已有完成组合追踪首次或重建`0x3F`的同一时序。由此区分“未产生完成”“被掩码挡住”“事件过早被清除”“停止前未排空”等原因，才决定最小设备修复。
