# Z72 与 Z6II 原始固件菜单本地复现报告

> 日期：2026-10-26；类型：授权离线固件分析与运行复现；flavor=null。

## 1. 结论

用户提供的 `Z72-fireware/Z7_2_0170.bin` 已完成身份及 CRC 核验，并在原生 Windows QEMU 中实际显示原始 Z7II C1.70 的 `PLAYBACK MENU`、响应向下导航。网上找到并固定的同机型 `xiaoqingfeng0526/nikon-z62-qemu` 又使本地原始 Z6II C1.70 显示 1024×682 菜单，并通过相同方向键验证。网页只传输按键并显示 QEMU screendump，不是网页假菜单。

**这是参考实验环境达到“原始 MENU 真实显示与输入”的本机验证，不是完整相机模拟器或新便携版本发布。** Z6II 使用明确标注的合成参数，非真实 NOR/校准恢复；主屏实验关闭，无 SD 卡，未启用捕获边界注入。旧 v0.4.0 严格探针和历史发布包保持不变。不连接相机、不刷机，不对签名、实时取景、拍摄或持久化作成功声明。

操作入口：[README-MENU.md](../profiles/README-MENU.md)、`start-z6ii-menu-reference.cmd`、`start-z72-menu-reference.cmd`。

## 3. 原生构建和宿主适配

构建使用隔离 MSYS2/UCRT64；运行只需本地 Python 与原生 EXE/DLL，不需 WSL/MSYS2/Docker。相对主构建增加 `--enable-pixman`，保持离线最小配置。运行目录各含 8 个依赖 DLL；清洁 PATH 下 `--version`、机器及属性列表检查通过。

| 程序 | SHA256 |
|---|---|
| `.build/z72-reference/runtime/qemu-system-arm.exe` | `6fd1c552ee6b14d2c7646a5ed92116fae86ecf2778911226fdf472e8fb8c312c` |
| `.build/z62-reference/runtime/qemu-system-arm.exe` | `3b6fb4b49664de3b2d1cfc557c2e0324e30904cc3da1cd91ba0002d2b34f6582` |

Z72 初次构建发现真实类型错误：`frame_count` 字段为 `uint32_t`，却调用 `object_property_add_uint64_ptr`。仅在生成源码将只读 QOM 注册改为 `object_property_add_uint32_ptr`；未改字段、计数逻辑、CPU 核心或客体。两个 profile 都需要该修正。保留初次失败与成功日志，不把编译错误掩盖为固件问题。

先完成 Z72，随后复用生成源码/对象树增量改为 Z62，节省重复构建；Z72 已完成的 65 个运行目录文件及其 manifest 未受转换影响。`.build/z72-reference/source` 与 `build` 现属 Z62 生成树，已置转换标记，不能用于直接重建 Z72。旧主项目 `.build/source`、`.build/qemu-build` 未改动。

宿主控制台使用 ASCII 临时目录复制受跟踪源码与校验后的成员，避免原生 Windows 的 Unicode argv 问题。适配仅规范斜杠、将 `/dev/null` qtest 日志设备改为 `NUL`，保留实际命令和会话哈希。固定捐赠工作树保持干净，未执行未跟踪辅助脚本。

## 4. 合成参数与原始执行边界

公开 Z62 项目通常需要真实 NOR 的组 17/18/32。升级包不含完整 NOR，本次也没有提取真实相机数据。因此另设必须显式选择的 `--experimental-parameters` 路径：

- 组 17 为 0x20000、组 18 为 0xA0000、组 32 为 0x180000；大部分为零，以 `ENDM` 结尾。
- 少数候选值来自公开 Z72 实验 fixture，不声称是真实 Z6II 校准或已识别硬件规格。
- 原始 Z6II Thumb 函数 `0x10302048` 明确加 `0xCE000`，读取 `+0x14/+0x15` 检查版本；据此使用组 32 偏移 `0xCE014`，不是 Z72 的 `0xBE014`。反汇编见 resource-version.asm（本地证据，未分发：`analysis/reference-qemu/z62/resource-version.asm`）。
- 参数记录明确 `experimental=true`、`factory_calibration=false`、`nor_dump=false`；没有恢复序列号、资源主体或传感器校准。

原固件未改指令、分支、返回值、应用索引或轮询限值。控制器电池/供电、内存和外设的实验合同仍是模型，不是完整硅片复原。Z62 状态确认 `main_screen_experiment=false`、`experimental_boundaries=0`、`sd_card_attached=false`，不借助可选主屏捕获边界制造菜单成功。

## 5. 本机显示与输入验证

| 项目 | Z72 | Z6II / Z62 |
|---|---|---|
| 原始应用索引 | 1（菜单） | 1（菜单） |
| 实际图像 | 720×480 PLAYBACK MENU | 1024×682 PLAYBACK MENU |
| 输入 | pin4，低电平按下后释放 | pin4，低电平按下后释放 |
| 可见结果 | Delete → Playback folder | Delete → Playback folder |
| 变化像素数 | 61,804 | 124,535 |
| 状态 | running、input_ready、无 error | running、display_enabled、无 error |

Z6II 初期约 51 秒墙上时间仅推进 3.747 秒客体时间，LCD 尚未开启；后续约 370 秒墙上时间、28.066 秒客体时间自然进入菜单。因此初期黑屏不能直接判为卡死。Z72 初次自动 MENU 未在原先观察窗口内切换，输入就绪后正常再次按 MENU 成功，没有强写索引。

Z72 曾做只读 GDB 观察：首次 interrupt 超时后安全 detach；后续状态查询成功并读寄存器，故障寄存器为零。仅观察到线程列表首包，**不声称已经逐核检查所有 CPU**。

截图原文件仅在本地忽略目录 `artifacts/reference-qemu/` 保存；JSON 中记录其 SHA256 与差异边界。此验收不是连续多次冷启动统计，也未遍历所有菜单。

## 7. 复现与剩余限制

项目根目录执行：

```bash
python tools/prepare_reference_firmware.py z62
python tools/run_reference_console.py z62 --experimental-parameters --port 8662
```

访问 http://127.0.0.1:8662；已有同端口实例时先用页面“关闭模拟器”退出。Z72 命令将 profile 改为 z72、去掉 `--experimental-parameters`、端口用 8666。两个 CMD 入口已实际通过原包识别和 `--help` 检查；该检查没有另启第三个模拟器。
最终完整回归实际运行 **86 项，全部通过，零跳过，耗时 60.872 秒**，日志见 E6；包含原生严格探针、RAW 离线验证及 23 项参考固件/控制台/构建测试。两个原始包、三份旧发布 ZIP、两个参考 EXE 共 7 项身份检查通过，`git diff --check` 通过。

后续固化的 `tools/build_reference_qemu.py` 使用新目录、固定来源、离线归档、精确 QOM 修正和清洁 PATH 检查，生成哈希 manifest；拒绝覆盖已有 runtime/转换树。13 项无编译测试通过，但没有用此新入口再次完整重编译；本机已运行 EXE 仍以 E2 的实际构建日志为依据。重建示例见 README-MENU.md。


- 没有实机连接、PTP、刷机或固件上传；签名/重打包/实机恢复方案仍未验证。
- 没有全菜单覆盖或多次冷启动统计，不能把一次导航扩大为全功能兼容。
- 实时取景、传感器、拍照录像、真实存储与设置持久化仍未验收；真实 NOR/校准数据仍缺失，但不再阻塞本次菜单验证。
- 原生参考二进制尚未作为新版本便携包公开分发；再分发前须做对应源码、许可证和依赖交付审查。
- 旧 v0.4.0 仍是严格无界面边界探针，不因参考环境成功而宣称其模型已实现整机启动。
