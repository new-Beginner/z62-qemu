# Nikon Z6II 1.70：双 EXPEED 6 协作分析报告

> 日期：2026-10-25；方法：离线静态分析；工具：Python、Capstone 5.0.7；报告类型：普通固件逆向（flavor=null）。
> **本轮恢复了软件控制协议骨架，没有验证实际芯片通信，没有修改固件或连接相机。**

## 1. 结论与边界

两份 master/slave 固件各有 `DUALEG` 任务，使用兼容的通道 1 报文封装、环形队列、通知接口和事件同步。已找到“主侧发请求—从侧执行本地步骤—从侧回复—主侧解除等待”的静态调用链。这支持“双 EXPEED 主从协调”的解释，而不是把一个 CPU 的两颗核心当作两颗 EXPEED。

主侧含 `APPCTL`、`APPMENU`、`APPLV`、`AFSVC` 等任务；从侧有 `MRAP_M`、`BACKEND`、`BE_REC` 等任务。但主侧也包含后端任务，**不能据此认定主侧只负责界面，或从侧独占 AF、降噪、编码等算法**。本轮没有恢复像素数据流、带宽分配或计算任务调度。

物理互连仍未证实。存在 PCIe、IPCU、ARM926 等字符串，但字符串不是当前 `DUALEG` 链路的硬件归属证明。远端地址窗口及实际中断路由未闭合，QEMU 还不能据此宣称已经支持双 EXPEED。

范围见 [scope.md](../../analysis/dual-expeed6/scope.md)：用户自有相机提供的本地固件；本轮无网络访问、无安装、无刷写。

| `eg1850_mas_01700.payload.bin` | 38,750,136 | `7b85aa96ea25d6b23481627313082476619ccb4dd3634a585de4ed896d350071` |

E-imports（等价锚点）：目标为裸 ARM/Thumb 固件 payload，不是具备常规动态导入表的 PE/ELF。本轮以任务表 getter/lookup、初始化调用者、发送封装、回调注册和分发函数作为等价依赖锚点，质量为静态直接指令证据；不据“无常规导入表”推断功能缺失。既有解包记录中的 CRC 成功不等于包头签名已验证。

代码候选加载基址为 `0x10020000`。初始化数据复制记录读取于 payload 偏移 `0xC018`：

| 角色 | 源地址 | RAM 目标地址 | 长度 |
|---|---|---|---|
| master | `0x123A1C14` | `0xC1800000` | `0xAEDB8` |
| slave | `0x1085C054` | `0xC1000000` | `0x17DC8` |

RAM 配置地址必须通过这组复制映射回文件，不能直接减代码基址。脚本先核对两份 payload 的完整 SHA-256，再使用固定锚点。

## 3. 两侧 DUALEG 任务与回调

任务记录为 28 字节：4 个配置字及 12 字节名称区。第二命名空间 lookup 使用 `task_id - 0x10000` 作为索引，再乘 28。

| 项目 | master | slave |
|---|---|---|
| 第二任务表 RAM 基址 | `0xC18AC5E8` | `0xC10161B8` |
| 第二表首项 | `SYSCTL` | `MRAP_M` |
| DUALEG 表内索引 | 137 | 41 |
| 真正任务 ID | `0x10089` | `0x10029` |
| ID 加载指令 | `0x10437730` | `0x1016480C` |
| 初始化调用指令 | `0x10437736` | `0x10164812` |
| 初始化入口 | `0x103E3140` | `0x10054FBA` |
| 任务回调（偶地址） | `0x103E3116` | `0x10054F50` |
| 初始化参数 r2 | `3` | `0x1F` |
| 接收处理器（偶地址） | `0x103E315C` | `0x10054FD6` |
| 接收注册入口 | `0x103E3198` | `0x1005500A` |

初始化调用者先通过任务 lookup 获取配置，再调用对应初始化入口，构成 ID→配置→初始化函数的直接证据。注册时使用 Thumb 函数指针（偶地址加 1）；两侧接收处理器均注册至槽位 1。

此前探索中的“合并两张表后的序号 288/94”不能充当任务 ID。另纠正旧笔记：从侧第二表首项不是 `SYSCTL`。这两项纠正不影响当前 `DUALEG` 定位。

## 4. 控制协议与请求—应答

### 4.1 收发调用链

- 主侧：`DUALEG` → `0x10206168` → 通道 1 发送器 `0x1038A72E`。
- 从侧：`DUALEG` → `0x1005E878` → 通道 1 发送器 `0x100611E6`。
- 两侧通用接收器按头部 channel 字节选择回调；主侧间接调用在 `0x1038A45E`，从侧在 `0x10060F16`。
- 主侧回调表注册函数为 `0x1038A86A`；从侧为 `0x10061322`。

以上是静态控制流，不表示这些路径已在真机或完整仿真中执行。

### 4.2 消息编号

| 主→从命令 | 从侧行为 | 从→主回复 | 主侧处理 |
|---|---|---|---|
| `1` | 置任务事件位 1；须与另一项本地就绪条件共同满足 | `2`，携带 10 字节 | 复制到 `0xC2B235C8`，再置主任务事件位 2 |
| `3` | 置任务事件位 4 | `4`，无载荷 | 当前主侧接收处理器没有分支处理 4；本轮未找到主侧发送 3 的代码证据 |
| `5` | 置任务事件位 8；任务回调调用 `0x10053F64` | `6`，无载荷 | 置事件对象位 2，与主侧等待对应 |
| `7` | 对本地对象 `0xC1012F88` 进行事件位 1 更新 | 当前路径无直接回复 | 业务含义未命名 |
| `8` | 置任务事件位 `0x10`；任务回调调用 `0x10053F3C` | `9`，无载荷 | 置事件对象位 4，与主侧等待对应 |

命令 1 的 10 字节回复不是无条件立即发生：从侧回调检查 `0xC1012F88+4`、`+8` 两个状态字均就绪。另一条件的完整来源尚未追清。主侧随后可通过已保存的函数指针上报 `0x030A0001` 和这段数据，但其字段意义未确认。

两条同步 API 尤其明确：

- 主侧 `0x103E30C0` 发送 5，调用等待封装 `0x1035D43A`，参数事件位 2；从侧回复 6 后，主接收器更新同一对象的位 2。
- 主侧 `0x103E30E6` 发送 8，等待事件位 4；从侧回复 9 后更新位 4。
- 两处等待参数 r3 都是 `0x1B58`（7000）。**尚未确认时基，不能直接写成 7 秒。**这些 API 也不能仅据等待调用就被描述为可靠传输或失败恢复机制。

### 4.3 环形队列与报文

主侧本地发送环地址为 `0xC7EF0000`，从侧为 `0xC70F0000`。这是代码所用本地地址，**不是已经核实的物理地址或两端共享地址映射**。通用接收路径通过配置表转换远端窗口，尚未闭合这一配置关系。

静态代码中的结构为：

| 项目 | 值 / 证据 |
|---|---|
| 槽位数 | `0xC0`（192）；主侧 `0x1038A812` 判断回绕 |
| 每槽跨度 | `33 × 8 = 264` 字节；主侧 `0x1038A7D0` 起的地址计算 |
| 环内记录起点 | 环基址 `+0x18` |
| 单条头部 | 8 字节 |
| 头部 `+0` | u32 消息编号 |
| 头部 `+4` | u8 逻辑通道（DUALEG 为 1） |
| 头部 `+5` | 本地递增计数器的低字节；不据此推断重传/可靠性 |
| 头部 `+6` | u16 载荷长度 |
| 头部 `+8` | 最多 `0x100`（256）字节载荷 |
| 建立时检查的常量 | `0x00C00108`、`0xAA550001` |
| 顺序控制 | 发送后、索引/通知操作附近有 `dmb sy` |

192 个槽位不等于可同时积压 192 条消息；代码有读写索引及满队列判断。本轮不进一步宣称实际可用容量。

这是小型控制消息通道，不能当作 RAW/JPEG/视频帧直接经过该环传输的证据。大块数据也可能通过描述符、共享窗口或 DMA 交接，但当前未证实。

## 5. 通知接口与处理器域的区分

主侧通知封装 `0x1038A2A2/0x1038A2C6` 最终调用 `0x102E0812`。后者将参数写至基准 `0x20136008` 和 `+4`，低层 `0x102E11A0` 按选择位决定是否加 `0x8000`。通用接收通知回调位于 `0x1038A488`，检查编号 `0x7F` 及通知位后读取队列。

这些证据确定了“消息环＋寄存器通知”的软件机制，但尚未将寄存器块通过可信符号或硬件资料认定为 PCIe/IPCU。

| 线索 | 当前能说明什么 | 不能说明什么 |
|---|---|---|
| master/slave 各有 DUALEG，协议及应答相配 | 强支持主从引擎协作解释 | 不等于真机链路已运行验证 |
| `CA7_CPU0_COM_RX/TX`、`CA7_CPU1_COM_RX/TX` | 固件有 CPU 核通信命名 | 不等于两颗物理 EXPEED |
| `Arm926IpcuService`（主固件） | 存在 ARM926 相关服务字符串 | 未建立它到 DUALEG 的调用链 |
| `IPCU_0`…`IPCU_15` | 有 IPCU 命名线索 | 未证明是当前跨芯片传输层 |
| `PCIE_OWN`、`PCIE_EP` 等 | 两份固件都有 PCIe 相关命名 | 不能仅据字符串认定 DUALEG 走 PCIe |
| `TwoChipConfKey` | 两份固件都有相同名称的配置键 | 不等于已恢复芯片间通道配置或工作分配 |

`TwoChipConfKey` 地址：主侧 `0x120AD20C`、从侧 `0x108334F0`；在两侧常量表中分别被 `0x107906CC`、`0x1016C08C` 引用，旁边还有 `DecodeParamKey`、`DecodeContextKey`。当前未证明这些键与上述通信对象的直接关系。按字节搜到的地址还可能偶然落在指令编码中，须有真实取址/调用上下文才能升级为代码引用。

## 7. 对 QEMU 的意义与尚缺部分

仅添加 `-smp 2` 不能构成双 EXPEED 模型。真实协作模型至少需要区分两个固件执行环境及各自局部内存，并解释远端地址窗口、环索引可见性、通知寄存器和中断。其内部 CPU 多核/ARM926 域应另行建模。

针对 MENU 的辅助模拟，可把这组已恢复协议作为后续从侧接口模型的候选边界；但必须先确认 MENU 启动实际依赖哪些消息。当前不能只伪造握手常量或始终回复成功就宣布原固件正确启动。

剩余问题：
- 10 字节回复的字段及其生产者；命令 1 的另一就绪条件。
- 两侧远端窗口的配置来源、地址翻译、中断路由，以及是否使用 PCIe。
- 命令 5/8 对应的本地业务阶段、超时单位和错误传播。
- 图像缓冲区所有权、DMA/描述符交接、AF/ISP/编码的实际任务分摊。
- 真机或硬件准确仿真验证；当前 MENU、双芯片 IPC 仿真均未实现。
