# Z6II 候选固件测试与 CAPCOM 握手 r6

本轮生成了新的 Windows 原生 QEMU，统一入口为 `start-z6ii-qemu.cmd`。它可运行已校验的原 C1.70，也能明确加载同布局的候选固件。新 CAPCOM GPIO 请求/应答模型补上了此前0x35通知链的缺口：两次独立冷启动各三轮菜单状态循环通过，完整固件状态列表均为空。完整取景、拍照编码、客体保存与回放仍未完成，**完整相机仿真目标保持进行中**。

## 1. 使用与产物

```bat
start-z6ii-qemu.cmd
start-z6ii-qemu.cmd --firmware "Z6_2_0170 (1).bin"
```

第二条以原包演示选择入口；测试自己的修改包时替换为实际路径。浏览器地址为 `http://127.0.0.1:8675`。CMD 明确启用合成参数、functional RAW、RAW completion、init-mode 和 CAPCOM sync。候选模式默认关闭自动MENU并显示健康状态未知。

## 2. 候选输入是真实执行

原入口只接受固定原版SHA256，不能测试修改。新入口接受两种明确输入：

1. 完整Z6II C1.70布局更新包：校验全部目录边界、成员名/偏移/长度、5个成员CRC和包CRC。
2. 三个完整成员文件：master.bin、slave.bin、controller.bin，固定长度且包含有效CRC尾。

读取后保存不可变字节快照，分别记录基线/候选SHA256、变化字节数和范围，每次启动再次核对暂存文件。原版入口的固定SHA限制仍保留。新入口不修CRC、不重打包、不修改输入原件。

CPU执行验证在临时master副本的入口放入 `mov r0,#0x62; b .`，只重算该副本成员CRC。r6实测 `PC=10020004、r0=62`，入口字节为 `6200a0e3feffffea`，正常退出。证据：[candidate-sentinel/report.json](../../analysis/z62-capcom-r6/candidate-sentinel/report.json)。这证明修改指令被执行，不代表这一测试副本是可用的相机固件。

统一CMD分别以原版及明确选择的候选包启动HTTP控制台，两者均响应MENU并正常停止；原版界面读取到完整空状态列表，候选界面持续报告状态未知。候选固定RAM地址仅作为未验证的观测，早期内存尚未初始化的异常会明确保留，不伪装成健康。

更新包中的 `_tpj01_v140.bin`、`vr1850_010100.bi` 仅校验并记录，未模拟其处理器，因此不执行它们的修改。CRC不是签名或真实性证明。

## 3. 0x35的实际缺口

旧r5仍在第二轮等待 `C18682AC mask8` 约3.016客体秒后失败。新一轮只读GDB追踪确认，下层请求和间接回调已经到达并正常返回，但异步应答回调没有运行。

从运行时句柄继续定位：

| 角色 | 句柄 | 真实读取到的合同 |
|---|---|---|
| 请求输出 | C1803AB4，资源65 | 04282018 bit8，高16位更新掩码 |
| 应答输入 | C18036FC，资源54 | 04282014 bit7，EXT索引0，IRQ65，回调102420A1 |

参考Z7源码中相同GPIO对属于独立CAPCOM握手，不是SPI包ACK，也不是RAW完成IRQ92。Z62已有模型仅处理其它控制器线，没有这对应答。

证据链：

```text
原固件输出请求沿
  → r6外设在100微秒虚拟时钟后提供应答沿（功能性假设）
  → IRQ65
  → 原固件102420A0
  → 102420D8发出03030024
  → 10241D66 / 10241C8C分派掩码0x10
  → 10241CDE产生03030004
  → 10396B6A / 10396EB6
  → 原固件自己的mask8事件通知
```

开启r6后的短窗口追踪实际命中了这条链，包含各级参数和回调地址：notification-trace/trace.json（本地证据，未分发：`analysis/z62-capcom-r6/notification-trace/trace.json`）。没有修改guest指令、软件事件对象、返回值、错误列表或应用索引；初始化one-shot和旧RAW桥也未被绕过。

短窗口追踪在2.023客体秒主动结束。沿用旧工具“必须复现0x35”的退出判据，因此该诊断命令返回1、`trace_complete=false`；实际是通知链已观察到而未去复现错误，不能将这个退出码当作菜单验收失败，也不能改写旧证据。会话正常detach并关闭，无运行/清理异常。

## 4. 原固件开启/关闭对照

同一个r6 EXE、同一原固件和参数。归一化临时目录及端口后，命令只差CAPCOM开关。按键时刻由运行时轮询决定，非完全相同指令时序；没有断点干预这些循环。

| 运行 | CAPCOM | 结果 | 观察终点（客体秒） | 完整状态列表 |
|---|---|---|---:|---|
| cycle-on | 开 | 三轮退出/重开/导航通过 | 49.586 | 全空 |
| cycle-off | 关 | 第一轮重开未进入菜单 | 22.487 | 全空，仍不算通过 |
| cycle-on-cold2 | 开 | 新冷启动，三轮通过 | 49.786 | 全空 |
| cycle-off-cold2 | 关 | 第二轮出现0x35，整体失败 | 36.872 | 包含0x35 |

两个开启组的每轮导航像素变化均为124,535、124,535、121,856；每组CAPCOM请求/完成计数均为3/3，合并0，从engine计数0。已打开保存的原厂菜单截图核对，不把菜单画面当成实时取景。复核脚本重新检查PNG哈希、真实像素差、固件与EXE身份及全部状态列表。

关闭组两次表现不同，保留原始记录；没有只挑复现0x35的一次，也没有把“没有0x35”当成成功。当前证据支持**本测试窗口内修复所追踪的握手缺口并改善重复菜单操作**，不证明无限次循环或所有启动时序稳定。

## 7. 范围与剩余工作

本轮只处理本工作区的离线QEMU、代码和测试产物，不连接相机、USB/PTP或物理存储卡；未提交或推送固件、转储、卡镜像。原包SHA256仍是 `5a9640b4c07abe1ecbf5a52655cbec6b893bba045bb2a1a1d21055b9f8f9d06d`。
