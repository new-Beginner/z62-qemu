# Z6II r105：状态驱动的菜单返回与采集停用

日期：2026-11-04。r105 是新的宿主观察／验收工具，沿用冻结 r104 EXE，没有构建或修改新设备内核。完整相机目标仍在进行；云端发布版本为 r104，默认仍 r75 界面／r69 内核。

本轮完成一次 30.000884916 客体秒的原厂窗口。第一轮 MENU 按真实应用状态推进，半按之前确已进入菜单；原厂随后返回拍摄界面，但新来源及预览未恢复，LCD 背景黑色。窗口正常结束、无宿主通信超时，不能据此认定旧超时根因已修复。实际 CPU 控制写入的重放证明，采集停止后没有再次武装所需通道；下一步应追踪原厂返回路径为何没有发出重新启动写入，而不是放宽 CW 配方或补 ready。

## 实现与开发原因

r104 的固定调度在菜单真正进入前已经半按，后续又有宿主通信超时，不能证明两轮恢复。r105 的 `RecoveryPlan` 因此只根据实际观察做下一动作：

1. 等 index3、已有有效四帧来源、实际预览、空固件状态以及输入队列／持有键均清空，稳定后才发 MENU。
2. 等 index1 真正进入、旧按键边沿已交付并稳定后才半按；不按固定秒数提前半按。
3. 返回 index3 还不足以通过。必须有预览计数增加，且四个不同来源都晚于半按、publication 大于旧集合，再验证 LCD 像素。
4. 第一轮满足新数据恢复后才允许第二轮；没有恢复便不重复按键、补通知或重启试验。

## 失败、纠正与源码归档

- 第一次 ASCII runtime 准备在启动前拒绝：普通 Path.resolve 将 Q: 解析为中文物理路径。改为复用已核对的 WorkspacePath；没有修改冻结的 host capture 工具或运行库，未因此启动／重启任何旧窗口。
- `state-driven-1` 在第一份样本因观察层先使用尚未读取的 `CW_preview_source` 而触发 KeyError。尚无源包，原生进程正常关闭；失败结果及4份原始源归档后，修正观察顺序，另建 `state-driven-2`，没有覆写失败。
- 一次误用“只接受完成verifier”的归档器因缺 `completed_evidence_check` 拒绝；随后用通用源码绑定归档器保存失败源，未修改失败结果。
- `verification-1/source-archive.json` 保存21份唯一来源；`control-replay-1/source-archive.json` 保存分析器与实际生成模型头文件两份；冻结 r104 构建和已有归档仍保留。
