# Z62 输入结果通知与帧对象链路研究

2026-10-29；范围：原厂 C1.70、离线 QEMU、Ghidra/Capstone 静态分析和 GDB/qtest 隔离诊断。

这是一份 r8 实施前的研究检查点，**没有发布 r8 二进制，完整 QEMU 目标仍未完成**。本轮确认了可消费的结果就绪通知组合，并把元数据通知追到原固件自行生成的非空帧对象。RAW 输出、结果通知、缓冲完成、停止排空应分别建模。统计像素、ISP 输出、持续取景、拍照保存和回放仍未通过验收；这些诊断不能证明真机刷入安全。

授权及边界沿用 [工作计划](../GOAL-Z62-QEMU.md)：用户授权在工作区实现固件模拟器。所有运行均为本地虚拟设备；没有访问相机、USB/PTP 或物理磁盘，没有修改原固件字节、CPU 返回值、固件软件事件对象或错误列表。故障诊断中的硬件状态事件明确记录为实验。正常入口仍为 [start-z6ii-qemu.cmd](../../start-z6ii-qemu.cmd)，继续使用 r6。

## P1：结果就绪通知

依据原版指令和校正后的回调恢复以下映射：

| 硬件输入事件 | `C269FA04` 位 | `C188808C` 事件位 |
|---|---:|---:|
| bank0 bit3，线路3 | `1` | `00100000` |
| bank0 bit4，线路4 | `2` | `00200000` |
| bank3 bit0，线路96 | `40` | `01000000` |
| bank3 bit5，线路101 | `8` | `00800000` |
| bank4 bit7，线路135 | `200` | `04000000` |

路径为硬件状态位 → 原固件输入 IRQ 分发 → 驱动回调 → RTOS 事件 → `102387B6` 内的 `10238804` 等待。组合事件为 `05B00000`，组合位图为 `24B`。

整组实验在 1.281 客体秒、已经完成 2 批原生 RAW DMA 且读回前 32 字节匹配后，供应一次上述线路。随后 1.353 秒的配对等待返回 1；下次等待恢复约 0.202 秒超时。该通知会被消费，不能简单作为永久启动就绪位。

`1023AE42` 调用等待后继续进入 `1023AD0C` 提交参数，不能仅凭该等待超时就断言它是黑屏的唯一原因。r7 的 bank4 bit8（线路136）仍是另一条缓冲组完成路径，不应混同于 bit7。

## P2：自然帧对象与元数据消费

被动组已经观察到 `04200001 → 1022F17A → 1022E03E(0)` 和 `1023123E` 帧处理任务持续运行，不能再把“没有帧对象”作为未经验证的假设。元数据消费 `10238A80` 在被动组没有命中。

元数据实验的关键顺序如下：

1. 第 13 个断点记录：1.266 客体秒，原固件函数返回对象 `C2CF2C40`，没有宿主构造或替换对象。
2. 1.328 秒，设备已完成 3 批 RAW；RAW 数据读回匹配；元数据控制寄存器 `20069F00=11`、bank0 中断掩码含 bit6。
3. 仅供应一次线路6；这是明确的诊断事件，统计数据仍标记未验证。
4. 第 18 个记录进入 `10238A80`；第 19 个记录在 1.331 秒调用 `1022E15C(041A0002,C2CF2C40)`，与生产端对象指针相同。

本轮证明了“硬件通知 → 原固件队列消费 → 上层非空帧对象”的连接。并未证明对象关联的全部数据已产生，因此没有把元数据通知加入自动 RAW 源。后续应读取对象 `+144` 上下文及 `+14C` 待处理标志，核对 `041A0002` 后的标志释放和 ISP 请求，而不是直接重复发 IRQ。

追加的对象所有权追踪（本地证据，未分发：`analysis/z62-frame-objects-r8/ownership-metadata2/trace.json`）已实际核对上述标志：对象 `C2CF2C40` 的 `+14C` 从 `40001` 经普通帧任务释放位1变成 `40000`；线路6诊断后，`1022E474` 传入释放掩码 `40000`，固件在 `1022DFCC` 自行写回0（记录点 `1022DFD0`）。上下文指针为 `C3C5A040`。这是固件自己释放资源，不是宿主清标志。

同一短窗口没有命中 `1023594E`。该函数有模式条件，不能据此断言所有 ISP 路径均未提交。下一步应区分当前统计/预览对象和拍照处理对象，再追踪真正的预览输出提交点。第一次 `ownership-metadata/` 运行因整段读取稀疏 MMIO 的空洞而拒绝，已保留失败记录并正常清理；重跑取消了未验证的整段读取，未改变设备响应。

## P3：停止和菜单时序

Z7 参考实现将底层停止 ACK、模块排空通知和公共序列结束分开。Z62 原版回调也有对应的不同路径：例如 RAW 排空进入 `10239128` 的 `41072800` 分支，修改 `C269FA08`；RAW 结果就绪属于 `41072802` 分支，修改 `C269FA04`。它们的用途和触发条件不同。

本轮 9.750 秒停止 `2EB` 前，`C269FA08=0`、`C269FA10=0`；`102383D4` 的条件限制没有建立正在等待的整组排空握手。未观察到 `041A0004` / `041A0006` 不能单独证明设备必须补发它们。第一轮菜单重开延迟 5.192 秒出现 index=1，与前一 r7 严格测试未重开的记录不同；GDB 会扰动执行时序，本轮亦未完成两轮视觉验收。保留原失败记录，维持 r6 主入口。

## 分析工具修复及可信边界

`tools/ghidra/ExportZ62Functions.java` 现在显式恢复六张已按 C1.70 字节校验的 Thumb TBB 表，然后建立尾调用边界，并导出 `.asm`。之前仅声明 RTOS 占位函数并不能阻止 Ghidra 在反编译阶段发现新分支，继而将 `1035C98C` 路径误分析到 `10104844`。

原 `input-lifecycle/`、`input-lifecycle-bounded/` 中含 `halt_baddata` 的伪代码保留为失败证据，不用来实现设备。优先使用 `input-lifecycle-tbb/` 的七个输入回调。`frame-object-callbacks/1022E15C` 仍有间接跳转警告，其 `.asm` 和动态参数可用，但不能把整个 C 导出当作经过确认的规格。`frame-object-route/1023858E`、`10238D02` 和 `frame-production/1023202C` 是未确认入口的探索种子，不用于结论。

`decompile_z62.py` 新增导出质量记录，缺少指令列表、坏指令、PIC/栈分析异常或跳转表警告会明确列出。`completed=true` 仍仅表示导出任务结束；`semantics_verified` 始终为 false。Ghidra 为已校验官方 11.4.2 包，使用 Java21 和 ASCII 暂存目录；每次运行保留原始/暂存镜像哈希一致性检查。技能索引中缺失的辅助路径未被当成已安装工具。

## 复现与下一实施门槛

在工作区运行以下命令；输出目录必须不存在：

```powershell
python -X utf8 -B tools/trace_z62_capture_setup.py --native-source --frame-start --input-drain --startup-waits --ready-set-experiment --virtual-limit 4 --output analysis/z62-ready-set-new
python -X utf8 -B tools/trace_z62_capture_setup.py --native-source --frame-start --input-drain --frame-objects --metadata-event-experiment --virtual-limit 2.3 --output analysis/z62-metadata-new
python -X utf8 -B tools/verify_z62_input_research.py
python -X utf8 -B -m unittest discover -s tests -q
```

探针新增无 RAW、错误像素、通知未使能、元数据模块关闭时拒绝事件的测试。全部本轮固件诊断已正常断开调试器并关闭所属 QEMU。r6/r7 二进制及绑定 manifest 已重新验证，哈希与前期记录一致；没有覆盖生产入口或设备源码。

本轮全量回归 `python -X utf8 -B -m unittest discover -s tests -q`：248 项通过、零跳过，耗时90.590秒。后续对象所有权追踪也已完成，未改变任何设备模型。

下一次实现应以真实帧对象为锚点，验证统计缓冲数据格式、提交/消费节奏和对象待处理标志，再建立独立 r8 设备层。必须在完整描述符校验和真实内存输出后发对应通知，并重新进行原生 qtest、无宿主事件注入的取景和菜单视觉检查。当前这些验收条件仍未满足。
