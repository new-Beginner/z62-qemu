# Z62 致命 Error、菜单重开与真实取景诊断

## 结论与边界

当前 Z62 原始 C1.70 的 Error 显示和 MENU 重开失败，均有本机只读断点证据指向采集状态 `0x3F`。状态在退出 MENU 前已经存在；退出只是回到 APPLV 后将它显示出来。再次按 MENU 时，固件确实收到请求，但菜单许可检查因该状态拒绝。本轮没有定位产生该状态的最初设备等待条件，因此不是完整硬件根因修复。真实取景及拍照还缺像素生产、Bayer DMA、ISP 输出及完整保存链验收，不能通过消除对话框宣称实现。

范围见 [scope](../../analysis/z62-capture-diagnosis/scope.md)。普通固件逆向，flavor=null；不连接实机、不刷机、不改客体指令、返回值或应用状态。断点会暂停虚拟机，时序结论须另作无断点复验。

## 1. 为什么退出后出现致命 Error

退出跟踪捕获：

1. `0x106316AC` 收到正常应用切换，R0=`0xC1824EB4`、R1=`0x10001`，此时 foreground 字节 `0105`，状态列表已经是 `[63]`。
2. 返回 APPLV 后 foreground 为 `0305`；`0x105B7E6C` 从 DSID `0x1921` 读取状态，匹配 `0x3E..0x44`。
3. `0x105B7EAE` 记录 R1=`0x3F`、R5=1；`0x10543034` 记录 R0=1，进入原始错误处理分支。

因此，现象更准确的描述是“采集错误状态先存在，返回拍摄应用后显示错误”，不是“EXIT 按键破坏了固件”。观察窗口没有四核 DFSR/IFSR 异常证据，且菜单键仍可进入固件处理，不能把这等同于 CPU 已崩溃。

### 状态来源已知到哪一层

静态确认的路径：`0x1026D434` 通知分发 → 回调 `0x1039710E` → `0x11909C58` 映射表 → `0x103970B4` → `0x1035B004` 状态追加。

- event9 表项地址 `0x11909CC4`，12字节为 `3f0000000000000010000000`。
- 分发器在相应优先级分支检查输入位8/位7，选择 event9；这里的位是软件通知输入，不应直接等同于硬件 IRQ 位。
- 本轮尚未动态捕获首次 event9 与首次追加0x3F，不能把静态可达路径写成已捕获的完整因果链。
- 未证明具体哪个设备命令、超时或停止/排空确认首先缺失；也未证明 `0x200600B0=0` 单独就是根因。

此前本地 sampling-source 开/关 A/B 均出现 Error 且均不能重开 MENU，所以仅移植 Z72 的采样开关不足以修复当前 Z62。

## 2. 为什么再次打开 MENU 失败

通过正常 `/key` pin9 按下、释放，在约3.3秒命中：

| 字段 | 实测值 |
|---|---|
| PC | `0x106231C2` |
| R0 | `1`（阻塞谓词为真） |
| R4 | `0x24`（表项索引） |
| R6 | `0x1094DD0C`（检查表基址） |
| R7 | `0`（检查列） |
| 状态列表 | `[63]` |
| pending MENU | `00000000` |
| foreground | `0305` |

检查表每项20字节，表项0x24位于 `0x1094DFDC`，函数指针为 `0x105B7E6D`（Thumb函数 `0x105B7E6C`），检查列值为0，因而执行该谓词。谓词返回1后，`0x106231C2` 执行 `movs r5,#0`，最终返回不许可。

这证明当前失败不是浏览器没有发送按键，也不是必须等到 event49 才发现卡住。40秒观察中没有命中 deferred setter `0x106217B8`、event49 consumer `0x10541790`、应用切换 `0x106316AC`；“未命中”只限这次窗口。不能据此保证清除0x3F后必然成功，后续仍可能遇到延迟请求或采集状态机的第二道阻塞。

Z72 文档包含不同历史运行条件下的重开结论，不能覆盖本次 Z62 实测。

## 3. 真实取景、拍摄距离当前实现多远

| 环节 | 当前边界 |
|---|---|
| 原始 MENU 与 OSD | 已有真实固件渲染、导航；不是网页仿制菜单 |
| 帧同步与采集配置 | 有部分模型及实验完成事件；不代表真实像素流 |
| Sensor 像素源/Bayer DMA | 未实现完整像素生产与传输 |
| ISP | 缺实际成像处理及输出；不能用 raw5 缓冲轮换或 memcpy 代替 |
| 取景视频层 | 没有有效图像帧送达并被原始固件持续消费的验收 |
| 拍照 | 未验证完整曝光/采集/处理/编码/保存事务 |
| 存储 | 上游 Z62 已报告4GiB SDHC/FAT32 B:挂载；这不等于照片保存成功，本机本轮未挂卡 |

依据：`third_party/z62-qemu/docs/z62-port.md` 后续章节257–284、315–331、434–466；`docs/z62-public-release.md`；`docs/z62-pitfalls-and-investigation.md`。port 文档190附近是较早状态，后续已新增IRQ和实验事件接口，不能把“没有IRQ接口”继续当作当前实现结论；但像素/DMA/ISP缺口仍明确存在。

重要区别：IRQ87组2 bit0 是错误通知（曾触发0x40），bit7 才是正常 frame-start。不能把错误 IRQ 当帧完成中断周期注入。实验边界或合成参数也不是真实传感器结果、NOR/校准数据。

## 4. 下一步最小可验证路径

1. 冷启动前布置 `0x1026D4BA`（筛选栈首字节9）和 `0x103970D4`（筛选R0=0x3F），记录首个通知输入、调用栈及相关命令/状态。向上追溯实际等待条件，不直接移植Z72自动重臂行为。
2. 仅在证明命令、掩码、结果与确认关系后补设备行为；验收错误状态自然消失、无注入重复 MENU→EXIT→MENU 可用。
3. 再实现可审计的像素源→Bayer DMA→ISP→显示缓冲；测试图案只能证明模拟成像管线，不代表接入真实物理传感器。
4. 最后独立验收完整拍照事务和可解码文件写入。卡挂载不能代替文件内容验证。

不要通过清空DSID、强制gate、改返回值或伪造完成消息绕过。这会掩盖设备缺口，并不能实现真实取景拍摄。

## 复核方法与剩余阻塞

在同一固件/构建上用正常pin0退出、pin9重开；通过QEMU RSP执行断点观察上述地址与寄存器，最终移除断点并detach。对应原始记录见 E1–E4；`timed_out` 表示其他候选断点在限定窗口未命中，最后T02记录是调试器主动中断，不是客体崩溃。

本轮交付诊断证据与报告，没有修改QEMU设备或固件，没有提交/推送。直接的软件拒绝原因已定位；首次采集错误的设备级根因、无断点完整冷启动复验，以及真实取景/拍摄实现仍未完成。

## 5. 继续推进：首次错误已动态定位到两个等待失败

本节是后续实验，更新前文“event9仅静态确认”的边界；旧记录保留用于对照。

### 新增证据

- `analysis/z62-capture-diagnosis/cold-first63.json`：原菜单基线冷启动，`1026D4BA` 的R4=`0x180`、LR=`1026DB93`、栈首事件9，状态列表为空；随后 `103970D4` 的R0=`0x3F`，映射记录为 `3f0000000000000010000000`。
- `cold-stop.json`：`102DBB9C` 入口R0=1、LR=`1026DB8F`；返回到 `1026DB8E` 时R0=`0x180`。
- `cold-stop-parts.json`：第一等待返回0，后续模式停止函数返回`0x100`；余下四个清理调用返回0。因此本次`0x180`确实由两个等待失败组成，而不是笼统的设备错误寄存器。
- `stop-wait-disassembly.txt`：对应原始指令及事件生产路径。事件对象为`C18A7634`。

| 错误位 | 实际失败点 | 等待内容 | 对应设备完成路径 |
|---|---|---|---|
| `0x80` | `102DBBAC → 1035D43A` 返回0，`102DBBB2`置位 | 软件事件`0x800`，等待参数100 | `102D7E26`回调处理IRQ92 bit1；状态`20065508`/掩码`2006550C` bit1；设置软件事件于`102D7E52` |
| `0x100` | 入口参数1选择`102DD9C8`，于`102DD9FC`等待失败，`102DDA02`置位 | 软件事件`0x20`，等待参数150 | mode0显式写`20065504`后，sync组2 bit10；状态`20060044`/掩码`20060040`；`102D7F34`设置事件 |

严格术语是“等待失败”：包装函数把内核错误折叠成布尔值，尚未捕获内核原始错误码，不能仅凭返回0断言一定是超时，也未核定100/150的时间单位。另一条参数0的mode2路径等待`0x10`，不是本次基线实际选择的分支。

路径：采集停止 `1026DB8A → 102DBB9C` → 两个失败位OR为`0x180` → `1026D434`事件9 → `103970D4`追加`0x3F` → Error/菜单拒绝。

### 两组已有设备完成源对照，均未通过菜单循环

保留原始固件、r1可执行文件与合成参数；只通过临时启动包装器追加已有QEMU属性，没有改设备代码。主屏实验关闭、捕获边界注入为0、无像素生产。

1. **三项组合（8665）**：`frame-start=on`、sensor `laboratory-frame-completion=on`、`laboratory-mode-completion=on`。初次MENU时曾读到空状态列表；正常EXIT/MENU后可看到原固件拍摄OSD、黑色背景，选定截图无Error框，但菜单没有重开。后续稳定按MENU再次命中同一表项0x24，状态`[63]`。证据：`completion-stable-reopen.json`及`artifacts/z62-capture-diagnosis/completion-cycle/`。
2. **完整握手组合（8667）**：在三项组合上增加input `laboratory-metadata-completion=on`、`input-command-completion=on`、sensor `laboratory-init-completion=on`和`init-delay-ns=250000000`。仍然初次菜单可用、退出后不能重开。证据：`artifacts/z62-capture-diagnosis/handshake-cycle/`与`handshake-master-cycle/`。未把主屏脚本的两次捕获边界注入带入实验。

两个组合都不是已验证修复，不能发布为“Error及重开已修复”。OSD出现不代表有取景图像。

### 调试覆盖限制与无效实验

- 循环探针会关闭自动MENU；控制台重启保留此设置。有一轮因此未自动进入菜单，已显式恢复后重测；该轮超时不计入修复效果。
- 对照配置下，一些函数断点在窗口内未命中，但之后内存中出现`0x3F`。显式选择主机核后仍未解决该覆盖问题；原因未明，不能声称已排除所有状态生产路径。
- 状态写监视实验最终在读取停止线程不可访问的地址时失败，finally已移除监视点并detach；该实验没有产生有效写入者证据，不能用来指认根因。

`tools/probe_reference_menu_cycle.py`原先只检查`menu_ready`，即使`reopened_menu=false`仍返回进程退出码0。本轮改为进入、退出、重开三个条件都必须成立；这修复的是验收误报，不是设备握手。
