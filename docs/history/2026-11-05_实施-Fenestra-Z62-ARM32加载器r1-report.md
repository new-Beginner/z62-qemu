## 2. 实现与身份

- 在独立 `fenestra/upstream` 源码副本上修改原 Fenestra C 加载器，而非另写 ZMOD 系统。保留 CC BY-NC-SA、EXCEPTIONS、NOTICE 等上游文件；本阶段未发布。
- 上游基线：`b199dcdfbb0ef536c6269ae5a9d97c376d488b8b`。仅修改 `include/fenestra_module.h` 与 `src/module.c`，增加可选的本地实验 ARM32 ISA／重定位值 `0x62000001`、4字节指针重定位、2字节入口对齐及32位地址范围检查。原 AArch64 默认行为保持8字节重定位。
- 保留格式长度、固件身份、SHA256、段边界、W+X拒绝、入口和重定位检查；失败时未写入目标镜像。当前是 v1 legacy `FxModuleServices` 日志入口，**不是完整 copied-service SDK 或原厂 native-service 后端**。
- 自写 Thumb 模块分别加载到两个地址，借助重定位后的字符串指针、内部 Thumb 函数指针，调用原 Fenestra 入口结构中的日志回调并返回。
- 使用现有自研 r69 `nikon-z62-dual-lab`，EXE SHA256：`37603d1f8c55f819c0e1d3808e670d2de562b954152f2d8b847d1068359296f9`。没有改 QEMU 的设备模型或客体成功返回值。
- 最终构建：`.build/fenestra-z62-0.1.0-dev.1-r7`，身份、命令、源码／产物摘要见其 `build.json`。新代码与复现命令见 [使用说明](../profiles/README-FENESTRA-Z62.md)。

本试验通过 QEMU 通用 loader 装载合成 ARM 程序，不加载 Nikon 固件。这一点既是安全隔离，也是证据上限：不能称为“已在原厂菜单中加载插件”。MMU／缓存仍为复位探针环境，元数据的 W+X 检查不等于已设置生产环境页面权限。

## 4. 真实失败、定位与修正

1. 初次链接未显式指定模块入口，Zig 驱动使用默认 `_start`，代码被回收；显式模块入口后得到偏移2和带 Thumb 状态位的符号。失败构建 r1 保留。
2. Zig 0.13／Clang 18 的驱动组合在原始 `sha256.c` 编译中触发后端软浮点错误；向量化、优化等级和 baseline 对照没有解决。直接使用固定的完整 `thumbv7-none-eabi` 前端及软浮点／无NEON参数后成功；没有替换或跳过 SHA 算法。不能将未经定位的 LLVM 内部问题概括为所有 Zig／ARM 工具链均不可用。
3. 首个运行未回执，CPU进入异常；加入只记录并停住的合成异常向量后，锁定 `LR=0x10021080`，其前一指令是工具链 `__aeabi_memcpy` 内的 `vld1.8`。复位环境没有浮点所有权，触发 UND。新增整数 ARM EABI 适配器，转入 Fenestra 原内存函数；没有启用浮点来掩盖问题。
4. 随后首故障为 `DFSR=1`、`DFAR=0x100232EB`，SHA256字节读取被合并为未对齐 LDR。对 C 前端启用 `+strict-align` 后同组输入通过；没有关闭客体对齐检查，也没有仅把夹具强行对齐。
5. GNU 工具链仓库索引及 GitHub 工具包下载未成功，未把不完整包当作可用工具；最终使用已固定的会话内工具链。编译器缓存及崩溃复现材料在 PI scratch，不写系统临时目录。

失败运行 `run-1.json`、`run-2.json`、`run-3.json` 与对应构建保留。首异常向量不重试原指令、不改返回值，异常仍判失败。
