# Z6II 采集拒绝与准备帧就绪等待 r77/r78

本轮已直接证明当前 r69 配置的采集工作被满队列拒绝，并将准备帧的主要耗时定位到原厂输入就绪等待。采集入队返回 0 时队列为 60/60，上层包装没有传递该布尔结果；后续准备帧反复在 `C188808C` 等待掩码 `05B00000h`，三次均约 201 毫秒后返回 0。具体缺少的设备完成条件仍未确定，本轮没有补通知或修改 QEMU 模型，不能宣布模式切换修复。

**r82 更正：**此前将 `C188808C` 首字 `01000111h` 直接当事件位图比较，是未经支持的解释，现已撤回。原始 Thumb 封装先解引用该首字，再将它作为 opaque 参数传入 ARM 内核 SVC；实际内核 flags 尚未解析。边界证据（本地证据，未分发：`analysis/z62-prepare-control-r79/event-object-boundary-1.json`）保留原始指令。超时、输出字 0、队列满及入队拒绝的动态证据不受影响，旧 JSON 字节和 SHA 不重写。

## 当前版本的采集提交确实被拒绝

| 顺序 | 原厂位置 | 实际观测 |
|---|---|---|
| 1 | `10325186` 采集提交入口 | callback `103EAE81`；原队列 60/60 |
| 2 | `1031627E`，刚从 `10225714` 返回 | R0=0，R4=`10320019`，R7=`103EAE81`；队列仍 60/60，无该新采集工作 |
| 3 | `103EC564`，采集提交包装返回 | R0=0；与入口同 CPU、同外层 SP，调用帧闭合 |

实际原指令交叉核对：`10225714` 比较 capacity/count，不满足容量条件时令 R6=0，再以 R0 返回；`1031627E` 下一条 LDR 立即覆盖 R0。外层 `10325186` 在该路径将 R6 保持 0，`1032529C` 返回 R6。因此 **上层返回 0 不能用来证明采集入队成功**，它不是下层入队布尔结果。不能把这三层不同语义混成一个“成功”。

这次证据来自正在使用的 r69/r76 配置，解决了 r76 报告中“当前入队返回尚未观察”的缺口。它没有证明所有版本／所有时刻的采集都拒绝，也不证明队列容量本身有错。

## 准备帧为何缓慢：已定位到 200 参数的就绪等待

r78 的四次观察均处于 r77 拒绝之后，没有再次发送快门或模式输入。

因此这些时长直接描述的是拒绝后的拥塞现场，不能单独证明全按前初始满队列形成的唯一原因。需要新的无全按对照，检查相同就绪等待是否在采集输入之前已持续发生；不重复已完成的旧 r68 场景窗口。

| 范围 | 配对结果 | 结论范围 |
|---|---|---|
| 准备帧 `103225C4` | 每组 3 对，约 201.9–202.6 ms，返回 `12h` | 不能把 `12h` 当作已完成图像 |
| 事件 15 `1023382C` | 3 对，约 3–14 μs，R0=1 | 此现场的主要耗时并非旧版本的事件 15 超时 |
| 设置应用 `102339EE` | 3 对，约 37–94 μs，R0=1 | 长等待在它之后 |
| `10232026 → 1023AE42` | 3 对，约 201.1–201.5 ms，R0=1 | 包含前置等待及后续参数重配置；旧探针标签 drain-buffer 不代表已完整还原硬件排空语义 |
| `1023AE4E → 102387B6` | 3 对，约 201.3–201.4 ms，R0=0 | 上述前置就绪检查失败 |
| `10238804 → 1035D43A` | 3 对，201.256438–201.401521 ms，R0=0，输出字=0 | 直接定位到具体等待 |

最后一行的实际参数：R0=`C188808C`、R1=`05B00000h`、R2=该调用 SP、R3=`C8h`（200）。调用和返回时该对象首字都为 `01000111h`，输出字为 0。该首字不是已经核实的内核事件位图，不能从它推断哪些 mask 位存在、缺失或中途变化；相关判断应依据真实生产者调用及尚待解析的内核状态。

`1023AE42` 的入参 `2EBh` 是选择位图线索，不能因数值相似就写成某个硬件命令编号。其包装先调用 `102387B6(mask,1)`，随后尾跳到参数应用路径；因此末尾返回 1 并不能反向证明前置等待成功。本轮实测恰好是前置等待返回 0、包装后来返回 1。

事件 8 只命中了一个可达的 return-site，没有配对 call。复核器将其留在 `unpaired_return_sites`，不计为一次返回 0 的等待。这是有意保留的证据边界。

## 复现与过程

先经 workspace 入口启动一个新的诊断会话／空软件卡，再把控制台打印的 session 绝对路径传给采集 probe。以下命令来自本轮，重复时必须替换新 session 和新输出目录，避免重放已有输入。

```powershell
$env:TEMP='<WORKSPACE>/.runtime/tmp'
$env:TMP=$env:TEMP
& 'Q:/.build/tools/video-r26/Scripts/python.exe' -X utf8 -B tools/run_z62_workspace.py --entry run_z62_action_queue_console --port 8688 --software-card artifacts/my-r77-card --diagnostic-output analysis/my-r77-faults
```

另一个终端：

```powershell
& 'Q:/.build/tools/video-r26/Scripts/python.exe' -X utf8 -B tools/probe_z62_capture_submit.py --session '<WORKSPACE>/.runtime/tmp/z62-reference-mli80mdo' --output analysis/my-new-submit-trace
```

后续三个 details/drain/ready 工具均接收同样的 `--session`、`--previous-trace`（已完成采集 trace 的 result.json）和新的 `--output`，不会发送控制。它们要求同一 PID，不能在重启后的 VM 继续旧 case。

本轮关键终态：

1. 首次 `trace-1` 在端口身份检查处失败，尚未附加 GDB、未发快门；记录保留。Windows TCP 的 State 枚举为空，但端点及 OwningProcess 可读。改用精确回环端点／RemotePort=0／正 PID，并再次核 EXE 同文件及命令行 GDB 地址；没有放宽为任意进程，也没有重启 VM。
2. DC34532 `trace-2` exit 0／5.93 秒；3 个关键命中、帧闭合、detach=OK，输入各一次；无 QMP 超时、late reply 或请求重放。
3. DC23400 r78 exit 0／13.46 秒；DC7048 r78b exit 0／17.06 秒；DC34740 r78c exit 0／15.89 秒；DC27236 r78d exit 0／15.26 秒。每组 3 包完整闭合、源不变、detach=OK，均无控制输入。
