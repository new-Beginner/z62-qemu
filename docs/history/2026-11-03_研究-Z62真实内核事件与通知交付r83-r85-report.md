# Z6II 真实内核事件与通知交付 r83–r85

本轮从原始 Z6II C1.70 的 ARM 指令恢复了事件 CB 寻址与 pattern 字段，并在同一台 VM 中实际观察到原厂将 pattern 从 0 写成 `00800000h`、setter 返回 0。随后 AND 等待 `05B00000h` 仍返回 `FFCE0000h`，其主错误部分为 -50；原始等待封装将非零错误转成布尔 0。已完成这条有限调用链的取证，尚未实现其它就绪生产者或修复模式往返。

## 范围与参考

仍使用冻结 r69 内核、r76 诊断控制台、原始 C1.70 和专用虚拟卡，无控制输入、无 guest RAM/寄存器写入、无 inferior 函数调用、无 IRQ 注入。断点/单步扰动时序，功能资格始终 false。

入口线索复用工作区 [nightglasses/z7ii-qemu](https://github.com/nightglasses/z7ii-qemu) 的 `docs/runtime/kernel.md`、`displaywait.md` 与 wait 研究，本地提交 `0e53ea5a6d4f3fc635d63c195a92e943370ac5e9`。其 RAM 地址没有照搬；Z6II 原始字节、表指针及 CB 身份另行核对。

公开语义参考为 [TRON Forum T-Kernel 2.0](https://github.com/tron-forum/tkernel_2/tree/5778f619bdb354443551888dc2e9aa191e684da8)，下载在工作目录 `references/rtos/tkernel_2`。它的等待服务编号为 `80360500h`，目标为 `80300500h`，**不同编号不能直接当作同版本证明**。只参考事件 AND/OR、置位及错误编码的概念；布局依据目标实际 ARM 指令。来源 URL、提交和四文件 SHA 已写入 参考记录（本地证据，未分发：`analysis/z62-kernel-events-r83/kernel-contract-1.json`）。第三方原许可保留，未将其代码并入设备模型。

## 实际目标布局与执行

| 项目 | Z6II 证据 |
|---|---|
| 封装对象 | `C188808C` 首字为 ID `01000111h`，不是 flags |
| 事件表全局 | 原 literal 指向 `C18AEC38`，现场 maximum=512、table=`C2C37808` |
| CB 地址 | 目标指令计算 `table + (low16(ID)-1)*32`，现场 CB=`C2C39A08` |
| ID / attr / pattern | 分别在 CB+8 / +10h / +14h；现场 ID 匹配，attr=8，pattern 地址=`C2C39A1C` |
| 原厂置位 | `101111BC..C4` 读取 pattern、与 set mask OR、再写回；host 只单步执行这一条原始 store |
| AND 条件 | `10111628` 的 BICS 验证 requested 中未满足的位；本次 mode=0 |
| 原始错误 | Thumb `1035D450` 在布尔转换前读到 `FFCE0000h`；外层 `10238808` 为 0，输出字为 0 |

完整 r85 轨迹中，等待开始时 pattern=0；原厂线路101通知在等待期间经过 setter，将同一个 CB 的 pattern 从 0 写为 `00800000h`，setter 返回 0。等待返回时真实 pattern 仍为 `00800000h`，相对于本次 mask 缺 `05300000h`。这次结论来自真实 CB 字段和原始指令，不再使用首字 `01000111h` 作位图比较。

此字段快照和一个调用链不能证明其它就绪位全局永远不会发生，也不证明传感器/ISP的全部硬件合同。下一步应核对对应输入3、4、96、135的合法生产条件，不能由统计101成功就替其它引擎发成功。

## 失败、恢复和完整窗口分开保存

1. r83 `events-1` 得到 setter 与 AND 检查的部分证据，但全局内核返回点被其它任务频繁命中，96次断点预算在目标返回前耗尽。随后观察器在运行态读内存导致 RSP 超时，cleanup 未完成。该结果保持 `completed_observation=false`，不回溯标成功。
2. 第一次恢复因移除不存在的断点返回 E22 而拒绝继续。第二次对本任务已知地址逐一验证插入/移除均 OK，解除调试并确认同 PID 的 VM 恢复 running。没有因超时重启 VM，没有发送相机输入。
3. r84 使用目标任务栈对应的 Thumb 封装返回点读取原始内核错误，避免共享内核返回点。增加运行态快照前暂停和完整异常栈保存。`events-2` 完整、detach OK、源未变。
4. r85 再观察等待期间的通知，实际得到 0→00800000h、内核返回0及后续 AND 超时。`events-3` 完整、detach OK、源未变。旧探针/回执字节保留，修订另建文件。

工具为 `z62_kernel_event_layout.py`、独立三版 `probe_z62_kernel_events*`、恢复工具、参考分析和证据复核工具。3项新专项验证 CB 索引/地址/ID 拒绝、真实 pattern 读取及任务栈过滤；实际原厂两次完整观察分别 exit0／9.68秒和8.18秒，证据复核 exit0／1.24秒。没有重跑旧 r68 或完整历史全量，没有重新编译或修改 r69。

P83（callflow）：原始输入101回调 → 内核 OR 写入同 CB → setter 返回0 → 目标 AND 等待的实际 pattern不足 → 内核负错误 → 原封装布尔0。此链解决了“调用是否被内核接受”的缺口，尚未解决其它数据引擎的生产条件。
