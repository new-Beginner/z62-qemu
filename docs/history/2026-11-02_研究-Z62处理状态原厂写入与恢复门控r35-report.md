## 授权与实现层级

`tools/trace_z62_processor_state.py`版本为`2026.11.02-processor-state-watch-r35b`。使用既有GDB原生写观察和原指令单步记录before／after，不修改guest状态。解析器要求完整4字节，缺失或截断不能变成状态0；两项新测试先失败后通过。

## 原厂恢复调用路径

三批新Ghidra输出共9个函数，工具退出0、原字节未变，结构检查均无列出问题；反编译通过不等于全部语义或设备合同已验证。静态摘要保存于restore-contract（本地证据，未分发：`analysis/z62-selector-r35/restore-contract.json`）。

| 原厂函数／字段 | 已确认静态行为 | 尚缺动态证据 |
|---|---|---|
| 103D2F1E | 以状态分支处理模式请求；参数+2为0时走状态4写入；状态2可调用103D2C52(1) | 本次完整请求缓冲和每个内部返回未逐项配对 |
| 103D2C52 | 处理待停止请求列表；非特定内部模式时设置C1864CD4／CD5，向C237A754请求0x8000工作 | 本次pending标志数值与具体队列内容 |
| 停止辅助末尾 | C237A874、C237A894、C237A8B4三个列表计数均0且C1864CD4为0，才请求C237A754的0x2000工作 | 哪个真实条件未满足，以及对应生产／消费链 |
| 103CE43E | 状态4分支处理队列、模式、服务与等待后，由103CE574写状态1 | 切换后是否再次进入、卡在哪一步或根本未收到调度 |
| 103CE3E6 | 检查C237A7B4／C237A794及节点标志 | 本次列表与节点快照 |
| 1034BEE6／1034BE62 | 原始指令分别取列表+8计数、判断该计数为0 | 只证明读取格式，不证明当前队列为空 |

这些0x8000／0x2000是原厂软件工作通知线索，不是可直接补发的设备IRQ。禁止宿主注入该通知、清队列或把状态4写成1来绕过实际完成条件。停止辅助中还存在其他事件、缓冲与模式分支；当前未将其缩减为单一硬件缺失。
