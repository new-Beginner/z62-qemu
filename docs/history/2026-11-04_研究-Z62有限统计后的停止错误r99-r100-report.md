# Z62 r99／r100：有限统计后的停止等待与 0x3F

日期：2026-11-04。普通固件研究，范围为离线固定 C1.70 与冻结 r98 QEMU。没有连接相机、USB/WPD 或物理盘，没有刷机、修改 AF、补 ready／事件或改原厂返回。默认 r75 界面／r69 内核保持；云端源码仍为已推送的 r98／f9ed1dc。

## 结论

已将 r98 末端 Error 进一步定位到原厂第二次停止调用的 `0x80` 返回位。r99 确认两批有限统计确实进入原厂消费者，随后原厂追加 `0x3F`；r100b 直接捕获第一次停止返回 0、第二次停止返回 80h，两个阶段的 mode 及四个清理函数均返回 0。原始指令证明 80h 来自 `C18A7634h / mask 800h / limit 100` 的前置等待失败。

这不是设备级根因修复。尚未直接捕获该等待 CALL／RETURN 与原始 kernel 错误，不能将它冒称为已核定的 FFCE0000h 超时；也没有证据支持直接补 IRQ92 或启用仅产生握手的软件替代来宣布恢复。原厂最终仍显示关机重开的 Error，preview=0，完整摄影／AF／刷机安全未验收。

## 新观察器及真实性边界

新增 `z62_failure_observer.py`、`probe_z62_current_failure.py`、`probe_z62_current_stop.py` 和 `probe_z62_current_stop_scoped.py`。复用既有 RSP 单步和所有执行断点撤除机制，使用 Z1 而非软件改指令。实际 live bytes 与原始 master 校验；动态返回断点绑定实际 LR、CPU 与原 SP。单步执行原指令，没有改寄存器、软件 RAM、返回值或 inferior call。

每个停点保存寄存器、256字节原栈、客体时间和完整状态表；scalar消费者额外保存原参数及输出。时间只描述该调试窗口，断点会扰动，不能当实机性能或无附加功能验收。

原始 master 是包含末尾CRC的38,750,138字节成员，SHA256 `bb83613121f843d65101da936d942acdc513d86dbd3abc26259d0d870d03f5d4`；裸ARM/Thumb固件没有PE/ELF IAT，等价依赖证据是已校验的原调用／返回、literal事件对象和动态参数。沿用既有Capstone／原始字节及已保存的Ghidra导出，没有启动IDA或安装工具。r98 EXE仍为`63531fbc8772c8cf370fab2d721eca96d8104022c08b674e94b65aae2cedfcde`，源码身份复核通过。

## r99：统计已被消费，3F由原厂追加

完整16.001479833秒窗口：31次accepted MAIN／CW、122次有限采样／2批；不同于无附加r98的33次，不能混用计数。实际调用：

| 调用 | 原厂时间／结果 | 限制 |
|---|---|---|
| 102301BCh → 原LR 102314CFh | 6,284,259,062ns入口；6,051,271ns后返回 | 外层消费者；不把R0单独当完整业务验收 |
| 10210B0Eh → 1023021Ch | 6,284,283,104ns入口；5,377,583ns后返回；输出8字节`01ffffff08000000` | R0=0不是已确认的错误码；保存真实输出，不编造算法语义 |
| 103970D4h → 103970D8h | 6,403,882,520ns，R0=3Fh；返回后列表由[]变为[63] | 原厂BL执行，48,584ns；没有由宿主写错误码 |

原栈含1026DA99h，原字节证明该上层路径在1026DA90h调用102DBB9Ch，1026DA94h将返回交给1026D434h。此前旧错误报告的1026DB8Ah是另一个调用点，不能直接套到本窗口。r99未命中直接状态35生产者，不能推断所有配置都不会出现35。

## r100b：真正失败的是哪一步

第一轮高频通知入口在正常逐帧路径上反复返回，提前耗尽128停点预算。保留完整16秒正常收尾、两项未返回和未捕获3F的事实；没有重启同一个进程或覆写原件。另建scoped-1，仅移除高频通知入口，保留停止／mode／清理／状态追加点。

scoped-1完整16.002262750客体秒，32次CW、122次有限采样／2批，23入口／23返回、无未返回项，detach OK、进程exit0，卡与源不变。

| 停止调用 | 第一次 | 第二次 |
|---|---:|---:|
| 输入参数 | 1 | 0 |
| 入口时间ns | 2,063,832,604 | 6,301,289,708 |
| 原厂总返回 | 0 | 80h |
| 后续mode分支 | 102DD9C8h（mode0） | 102DD964h（mode2） |
| mode返回 | 0 | 0 |
| 清理102FB41Ch／102FB62Ah／102FB702h／102FCA50h | 各0 | 各0 |
| 入口到mode入口ns | 5,375 | 101,203,187 |

第二次总返回时间6,403,615,875ns；3F追加在6,403,628,645ns，顺序明确。原始102DBBACh调用1035D43Ah，r0从literal读取C18A7634h、r1=800h、r3=64h；若布尔返回0，102DBBB2h将r5设80h，之后与mode和清理结果OR。实际嵌套返回均0，因此80h来自这个前置等待失败，不能再归因于本窗口mode0／mode2返回非零。

约101ms的间隔与这一等待相容，但本轮没有直接采集其原始kernel返回，报告只称等待失败。静态回调102D7E26h检查输入bit1，并由102D7E52h向同事件发布800h；既有研究将其对应到IRQ92的20065508h／2006550Ch bit1。这个静态关系不是本轮已动态证明的全部设备完成链。

原厂此前已将MAIN高度1342改为136并主动停CW。旧传感器的`laboratory-frame-completion`是单独的仅握手实验，不能因为它可能满足等待而直接用来证明当前真实读出完成；同样不能增加旧RAW计数或补ready。下一阶段要确认该136行阶段的提交、实际数据资格、rearm／W1C与完成条件，再决定是否需要独立设备实现。
