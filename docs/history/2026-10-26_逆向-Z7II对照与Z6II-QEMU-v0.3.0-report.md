## 1. 交付结论

已从 GitHub 搜索并拉取 [JKWTCN/z72-qemu](https://github.com/JKWTCN/z72-qemu)，固定提交 `f6b80ec650116a6b0117d31f9ea112b05bb7f52a`，读取其板型、配置设备、双引擎视图、研究文档和验证方法。本轮据此独立恢复 Z6II 1.70 原固件的早期配置与首批系统写入，并实际编译 Windows 原生 QEMU v0.3.0。不是仅转述 Z7II 文档或添加启动脚本。

**41 项测试全部通过、无跳过。** 原生 QEMU 与独立 Unicorn 的全部 72 次成功配置访问逐项一致；原厂两次延时循环没有被跳过。原固件在首次读取 `0x20022300` 时按严格策略停止，尚未进入完整 RTOS/MENU，也尚未连接 Z6II 双 EXPEED 传输。

## 2. 找到哪些共性，哪些不能照搬

| 项目 | Z7II 固定提交 | Z6II 本轮独立证据 / 决策 |
|---|---|---|
| 载荷执行基址 | 两角色均 `0x10020000` | 相同；不可把两份固件直接装入同一个全局地址空间 |
| 启动 SRAM | `0x04008000` 起的实验性 4 KiB | Z6II 相同，临时栈顶 `0x04008F00`，已支持 |
| 首次配置 | `0x04264000=0x21`、`0x04264020=0x153B0902` | 两侧原始指令相同，本轮加入被动存储 |
| 读改写配置 | `0x04281028/2C` | Z6II 两侧配置例程均在 `0x1002D700`，不同于 Z7II 从侧偏移 |
| 延时循环 | 40,000 / 8,000 参数，返回 `0xFFFFFFFF` | Z6II 两侧实际执行并核验，不修改寄存器或分支绕过 |
| 系统首批写入 | 58 次写入、57 个不同地址 | Z6II 两侧的地址顺序与 Z7II 相同，但两处值不同于 Z7II 主侧 |
| 系统配置入口 | Z7II master 偏移 `0x4C6C`；slave 低分支 `0x361C` | Z6II 两侧均为 `0x35D0`；必须按本机指令恢复 |
| 主侧初始化数据 | Z7II `0xB1800000` | Z6II `0xC1800000`；不复制 Z7II 主侧 B 段 RAM/堆地址 |
| CPU/GIC | 源码选择 Cortex-A7、CBAR `0x04000000`、GIC revision 1；部分文档仍写 v2 | 上游也注明实验假设；本轮不凭同平台断言真实硬件型号，保留本地执行假设 |
| 双引擎 | 私有 CPU memory view、共享 RAM alias、双向 GPIO；不是单纯 SMP | 架构可借鉴，但 Z6II 远端窗口和 GPIO 位尚未本地验证，未照搬 |
| PCIe | 上游配置实验不等于真实端点转发、DMA/MSI 实现 | 不把“链接状态模型”当作 Z6II 实际传输证据 |
| 菜单/显示 | 上游存在针对 Z7II 的函数偏移和补丁实验 | 不用于 Z6II；本轮全部执行原始 payload |

关键差异已经写入机器可读证据，而不是只在文档中提醒：

| 寄存器 | Z7II 主侧源码契约 | Z6II master 原始执行 | Z6II slave 原始执行 |
|---|---|---|---|
| `0x200300B8` | `3` | `1` | `1` |
| `0x2002010C` | `0x303` | `0x101` | `0x101` |

Z6II 首批写入与 Z7II 从侧 bit-2-clear 分支契约相同。**这只能证明该批配置相同，不能证明芯片角色、内存容量、传感器或图像处理分工相同。** 比对通过 AST 字面量读取上游表，不执行上游 Python 代码；本轮未取得或独立运行 Z7II 固件。

上游双引擎实现依据：其 CPU/GIC 初始化（本地证据，未分发：`<WORKSPACE>/third_party/z72-qemu/qemu/nikon-z72.c:2425`）、对端窗口/GPIO 互联（本地证据，未分发：`<WORKSPACE>/third_party/z72-qemu/qemu/nikon-z72.c:2676`）。历史研究中既有调试器替代写入，也有后续同机双引擎演进，不能将两种实验混为一谈。

## 3. 本轮实现

[板型源码](../../qemu/nikon-z6ii.c#L45) 新增四个早期配置字与 57 个首批系统配置字，共 61 个 uint32 位置，支持小端存储、原厂读改写、机器复位清零。零复位值明确是实验初始条件，不声称恢复了真实时钟/供电/引脚效果。

两个 MMIO 容器仅接受表内精确字地址；表内空洞、1/2/8 字节访问和非对齐访问拒绝，记录真实绝对地址，不返回有效的未知设备应答。`0x20022300` 不在配置表内；不生成固定就绪位，不替代完成通知。

- `--trace-config` / `trace-config=on`：记录全部成功访问，结构化报告保存 `configuration_accesses`。
- `--no-boot-config` / `boot-config=off`：负对照，准确退回 v0.2.0 的第一次未知写入。
- 版本同步到板型、构建器、启动器、清单和 ZIP。保留固件 SHA-256/长度检查、本地调试端口和严格错误退出。
- [独立证据生成器](../../tools/analyze_boot.py) 从本机原始固件复现访问、指令、延时和比较结果；不是按 Z7II 偏移修改固件。

## 4. 执行路径与验收

P1（path_type=callflow，E-local/E-native）：原始复位分支 `0x10020000 → 0x1002BC88` → 六组 CPU 模式栈初始化 → 两次配置写入 → `0x1002D700` 的原始读改写和两次延时 → `0x10020394` → `0x100235D0` 的 58 次系统写入 → `0x100208D4` 轮询器 → 在 `PC=0x100208E0` 首次读取 `0x20022300`，记录现场并以代码 2 结束。

原始参数是 `r0=0x20022300`、`r1=1`、`r2=40,000,000`，轮询条件为 `(read & r1) == r1`。本轮不供应这个状态，故没有宣称成功通过内存初始化。

- 独立 Unicorn：每角色 96,241 个 pre-instruction hooks（包括停止读取指令）。这是探针计数，不是声称 QEMU 提供同一指令计数器。
- 每角色成功访问 72 次：66 次写入（8 次早期、58 次系统）和 6 次读取；原生 QEMU 的地址、值、宽度和 PC 与独立轨迹完全一致。
- 原厂延时分别以 40,000 / 8,000 进入，减计数循环正常返回 `0xFFFFFFFF`。
- 两角色的预置值实验均验证位保留；原生 QEMU 核对原始 16 KiB 页表逐字节不变。预置只作用于单独实验实例，不属于原始复位场景。
- 所有 61 字均验证读写及复位；1/2/8 字节、未对齐和空洞访问负对照通过。通过临时 SRAM 合成指令验证 CPU 的无效访问也确实记录并以 2 退出，不只是调试器返回错误。
- 新旧根 CMD、解压包 CMD、含空格解压路径和无 MSYS2 PATH 的执行均通过；ZIP 完整性/摘要与程序/依赖摘要通过。
- 原始固件 SHA-256 未变，两个上游参考仓库工作树未变；未连接相机、未刷写、未上传固件。
