## 结论与范围

**本轮完成观测、验收修正和故障定位推进，没有完成稳定 MENU 循环或取景修复。** 显式 `init-mode` 在保存的延迟组中支持一次无状态码的重开和导航；三循环实验第二轮出现 `0x35/0x3F`，第三轮显示原固件 Error。静态找到 `0x35` 的真实构造及上层等待失败路径，但尚未动态确认本次命中的具体调用点。不能移除初始化 one-shot 限制或无条件重复发 IRQ 来冒充修复。

范围：用户授权继续本地模拟器开发；详见 [scope](../../analysis/z62-z6-transfer/scope.md)。本轮未访问相机、未发送 PTP、未刷机、不修改 guest 指令/返回值/错误列表，不启用主屏辅助启动。合成参数不是实机 NOR/校准；没有 RAW 像素、DMA/ISP、拍照保存或持久化验收。没有重编译设备、提交或推送代码。

### 重复运行的时间线

以下时间属于三循环无断点样本：

1. 1.372秒：master 初始化提交3、完成1。
2. 15.168秒：首次观察到 mode=`0x8000`（mode2）、config=`0x10011`，mode完成1，状态空。**mode2早于0x35，不是报错后才出现。**
3. 24.506→24.658秒：提交4→6，初始化完成仍1。
4. 首次0x35在(30.311,30.470]秒，阶段after-reopen、索引3、pending=`0x20000`。

## 0x35 的新静态定位

有界脚本（本地证据，未分发：`<WORKSPACE>/analysis/z62-z6-transfer/analyze_status35.py`） 校验固定主成员哈希并解码关键窗口；输出 `status35-disassembly.txt`。裸 ARM/Thumb 成员无 PE 导入表，等价基础证据为输入哈希、PC-relative字面量消费者和真实调用/写指令。字面量池和TBB表的机械解码不是可执行代码证明。

已证实的静态路径：

- `10397EC8` 输入r0=2时，`10397EE6` 生成0x35，构造 `{code=0x35,value=1,mask=0x20}`；`10397EF8 → 103970B4`，再经已知 `103970D4 → 1035B004` append路径。
- 五个候选等待调用 `103999BA / 103999FC / 10399BD8 / 1039C1F4 / 1039C318` 使用上层对象 `C18682AC`、事件mask8、limit=`0xBB8`；失败返回0后进入上述上报，调用点分别为 `10399A2C / 10399A2C / 10399BF8 / 1039C224 / 1039C320`。
- `1035D43A` 将底层非零错误映射为0、成功映射为1。当前只能称有限等待失败，未证实所有错误必为超时，也未确认limit时间单位。
- 候选完成侧：`10396B6A` 收到通知 `03030004`，经过 `10396E74` 分支到事件mask8设置路径；还没有将通知实际产生过程串到IRQ92。
- `10399E42` 看似立即数0x35的字节实际上位于TBB表，不是状态生产证据。十进制35（0x23）也不能与十六进制0x35混淆。

**未证实：** 本次循环命中了哪一个候选等待；上层mask8失败与下层mask800/mask20、初始化one-shot的完整因果链；0x35是否单独足以阻止MENU。当前模型同时有一次性guard及mode0条件；mode2快照不满足后者，不能只删guard。

下一轮最小动态定位应在原固件执行断点 `10397EC8`（r0=2）记录LR，再按实际caller过滤 `1035D43A`（r0=C18682AC且r1=8）及返回点；辅助观察 `10396B6A`（r0=03030004）。不改guest字节或返回值；断点运行与无断点时序数据分开。
