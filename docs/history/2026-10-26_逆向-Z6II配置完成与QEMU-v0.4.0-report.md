已在本地建立 `main` 分支，中文基线提交为 `f7aa580`：`feat(模拟器): 建立 Z6II QEMU v0.3.0 开发基线`。随后实际完成 v0.4.0 双通道配置实验模型、Windows 原生构建和回归。没有自动创建远端或推送。

## Evidence → Finding → Path

### 1. 精确配置范围与命令反馈

**Evidence：** `tools/analyze_platform.py` 独立 Unicorn 模型和 `analysis/qemu-v0.4.0/platform-evidence.json`；真实 QEMU 轨迹位于 `verified/`。两侧成功轨迹完全相同，每侧 428 次访问：

- 368 次写入（8 次早期写入、360 次平台写入）。
- 48 次状态读取、6 次结果读取、6 次早期读取。
- 实际访问集恰为 346 个字：4 个早期字和两通道各 171 字，无未访问候选残留。
- 40 对命令/状态；`0x20023118` / `0x20043118` 接受 `1,0x10001,0x20001,0x30001,0x40001`。其他命令字仅接受各自观察到的值。
- 两个结果地址 `0x2003016C` / `0x2005016C`。

**Finding：** 原固件的写命令→读完成位→写 `1` 确认序列与命令驱动/W1C 模型兼容。此前把条件存储误读为写零的判断已由实际轨迹纠正。最后两组读取 `0x2002E300` / `0x2004E300` 后，固件再次确认前一组状态，因此这两个最终状态保持 1；模型没有擅自替固件清除它们。

**Path：** `qemu/nikon-z6ii-platform.h` 固化稀疏地址/合同，`qemu/nikon-z6ii.c` 实现通道隔离、只读结果、W1C、复位和严格错误访问。绝不把整个 MMIO 窗口当作可写 RAM。

### 2. 四次真实返回，不做分支替换

**Evidence：** GDB 在以下原始 PC 观察返回值；独立探针保存相同值和 SP，默认两侧均为 `[0,0,0,0]`：

| 观察 PC | 对应调用 |
|---|---|
| `0x100203A8` | 通道 1 第一类配置 `0x100235D0` |
| `0x100203B0` | 通道 1 第二类配置 `0x10023CC4` |
| `0x100203BC` | 通道 2 第一类配置 |
| `0x1002BDC4` | 通道 2 第二类配置经尾调用返回主启动 |

**Finding：** 四次配置调用可以在明确的设备假设下通过原始指令执行结束。包装函数最后为尾调用，不累积前三次错误：最后值为 0 并不意味着前三次没有失败。两个配置通道也不是两颗 EXPEED。

**Path：** 保留 `platform-config=off` 复现原 61 字模型：每侧仍仅 72 次成功访问，严格停在读取 `0x20022300`、PC `0x100208E0`。`boot-config=off` 则恢复写 `0x04264000`、PC `0x1002BDA4`。

### 3. 负对照真实执行超时/错误路径

**Evidence：** `tests/test_platform.py`、`tests.log`、`result-failure/`：

- 两侧阻断 `0x20024100`：GDB 在原始轮询入口检查 `r0=0x20024300,r1=1,r2=40000000`，不改寄存器/PC，实际等待返回 `[0,0x4000,0,0]`。
- 两侧关闭自动完成：346 字仍存在，首个状态保持 0，原始超时后首配置返回 `0x4000`。
- 两侧结果注入 1：真实返回 `[7,0,0x70000,0]`；各 516 次配置访问与独立探针逐项匹配。
- 所有 40 对验证正确/非法/越界阶段命令、W1C 写零/无关位/置位确认、通道隔离；软件不能直接把状态写成就绪。
- GDB/QMP 检查全部字、真实复位、结果只读和复位后注入值保持；空洞、非 32 位及未对齐访问严格拒绝。

**Finding：** 完成反馈不是不加条件的“固定就绪”；反馈关闭或结果失败会改变原始执行路径。成功值本身仍依赖实验设备的假设。

**Path：** 启动器暴露 `--no-auto-complete`、`--blocked-control`、`--completion-result`。超时负例禁止逐访问日志，避免生成数千万行输出。未知阻断地址会报配置错误，而非悄悄忽略。

### 4. 精确 PC 日志修复

**Evidence：** 首轮真实 QEMU 比对有两处仅 PC 差一条指令：访问索引 81 的 `0x2002350C` 和索引 421 的 `0x2004E704`。原始反汇编确认应分别为 `0x100237FC` / `0x100243FC`，而非前一条地址。

**Finding：** ARM TCG 在少数连续 MMIO 写入时，缓存的 `env.regs[15]` 不代表精确访存指令。地址、数据、宽度和顺序并未出错。

**Path：** 用 QEMU 10.2.4 的只读 `cpu_unwind_state_data` 结合 ARM `CF_PCREL` 布局计算诊断 PC，不调用状态恢复接口、不修改 CPU。重新构建后，两侧 428 项轨迹的 PC 也全部一致，原测试未放宽。

## 复现

```bash
python tools/analyze_platform.py
python tools/build_qemu.py --msys-root <本机MSYS2-UCRT64根目录> --jobs 8
Z6II_QEMU_REQUIRED=1 python -m unittest discover -s tests -v
python tools/run_qemu.py --engine both --trace-config
python tools/run_qemu.py --engine both --no-platform-config
python tools/run_qemu.py --engine master --blocked-control 0x20024100 --timeout 60
python tools/run_qemu.py --engine both --completion-result 1
```

本轮全量测试耗时 50.931 秒，56 项 OK，无跳过。便携验收摘要为 `analysis/qemu-v0.4.0/acceptance.json`；含空格路径、干净 PATH、三个版本根入口、包内 CMD、ZIP 完整性、无固件和全部摘要均实际检查。`SHA256SUMS.txt` 可用 Git Bash 的 `sha256sum -c` 验证。

## 未实现与后续边界

同步完成、零复位、W1C、非法命令清就绪、默认结果 0 仍是**实验假设**，不是已恢复的硬件时序或内存训练。没有实机寄存器读写比对。CPU/GIC/频率/容量也仍是工作假设。

下一处真实边界为 `0x20016020`，主启动随后还有相邻地址写入；需要独立恢复其语义并继续原始 RAM/BSS 与启动流程。RTOS、中断、控制 MCU、双芯片窗口/通知、LCD/原始 MENU/输入与图像处理尚未完成。本报告不把此阶段称为完整相机模拟器。
