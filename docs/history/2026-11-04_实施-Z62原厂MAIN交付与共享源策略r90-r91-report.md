# Z62 r90／r91：原厂 MAIN 交付与共享源策略

2026-11-04。原始C1.70执行窗口已出现真实CaptureWork DMA及原厂CPU ACK：**13次设备完成、13组W1C，其中保存6帧、9,138,504个样本逐像素核对一致**。实现为A原厂受控入口执行＋C显式MAIN／像素后端＋有限设备传输；下游统计／ISP尚未接上，LCD全黑，完整拍摄、AF和刷机安全仍未验收。[范围](../../analysis/z62-capturework-original-r90/scope.md)。

## 首轮为何没有DMA

`original-1`使用固定r89。21次MAIN发布被输入缓存接受，但设备完成数为0，配方拒绝增加；原厂在packing提交前实际写了`20069530=00200040h`，r89只允许该字段为0。

这个值在旧r86状态中已经存在。r89原生夹具只复用了几何／LUT，给该字段写0，导致测试未覆盖真实值；这是夹具覆盖遗漏。首轮请求16客体秒，达到180秒wall limit时仍未完成目标窗口，结果保持失败，原进程正常exit0。其驱动及生成宿主源已另行归档，没有覆写。

## r91的修正和边界

新开关`nikon-z72-input-config.z62-capturework-policy0=on`明确选择本项目外部C-MAIN策略，要求CaptureWork同时启用。它只兼容0及已观察的`0x200040`；其他非零值如`0x200041`继续拒绝。物理源对的选择功能没有实现，不能据此评价修改物理路由寄存器的固件。

输入仍要通过MAIN／linear16／RGGB／CRC／时间身份验证，配置资格、LUT、ring／RAM、代次、DMA和ACK检查不变。提交的共享源字随输出保存在`output_shared_source_word`，不会拿后来变化的影子值冒充旧帧。像素数学和原厂软件状态未改。

## 原厂代码实际做了什么

输入时间取自`04266008`起的完整64位计数和频率，帧号按30 Hz规则计算；几何必须来自实际寄存器，0、裁剪低半字、奇数CFA或超界尺寸会拒绝，不回退到r86常量。没有等待旧预览ready后才供给MAIN。

原始主／从／控制器成员在运行前后都按固定SHA验证；沿用受控加载入口、明确的合成参数和既有实验握手。实际命令没有合成执行循环，也没有用户控件操作。新写入仅为MAIN源文件；FW trace中13次`20068210=18h`及13次`20068290=80h`均由master CPU产生，设备计数为13，完成状态最终清零。它证明原厂中断处理执行了ACK，不直接证明高层工作完成。

保存的输入publication为2…7，每帧1,523,084样本。第一次输入可能在配置提交前被代次规则淘汰，不能把14次缓存接受写成14次DMA。客体RAM读回分块、非原子，但全部保留载荷的样本与对应输入／冻结LUT一致；原厂窗口没有额外证明padding保持，相关保证仍来自单独的原生测试。

## 就绪和黑屏：已观察与未知

603次状态采样中，真实事件CB解析成功的pattern分布为：0共424次、`08000000h`共17次、`04300000h`共159次。最后值为0，不能据此说整段一直为0。没有采样到`pattern & 05B00000h == 05B00000h`，但本轮没有断点跟踪setter／返回，也不能断言采样间该条件从未瞬时满足。

最后ready_join=1、input_inhibit=1，准备队列头仍记录60项；持续统计0帧，原因`source`；预览0批，原因`reset`。grid显示`disabled`，这是当前窗口配置下的状态，**不能把它直接说成硬件没有完成**。CW来源尚未通过类型／域／所有权接口交给旧统计及ISP，旧raw-stream计数0也不能通过加计数来伪装。

最终1024×682 LCD已直接查看并逐像素检查，全黑：原厂LCD（本地证据，未分发：`analysis/z62-capturework-original-r90/original-2/final-lcd.png`）。文件和无错误列表不代替功能验收；当前仍未贯通取景或原厂拍摄。

## 保护、复用和下一步

两窗口的专用虚拟卡源SHA连续一致，snapshot=on，进程正常退出；没有访问相机、USB、WPD、物理盘或刷写。所有新源码、编译、缓存、包、DMA、日志及归档在工作目录，默认r75／r69入口保持。当前环境没有RawPy，701项不称为又重跑LibRaw。
