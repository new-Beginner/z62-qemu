# Z62 视频来源包、几何写入和独立跨度：r56

日期：2026-11-03，`flavor=null`。范围见 [scope](../../analysis/z62-paired-source-r56/scope.md)。延续任务一的模式／视频数据链研究，只进行本地仿真和原字节分析；没有相机、刷写或发布。

## 结论与实际失败

已取得三阶段原厂实参：照片1514×1006／row2272，视频1516×854／row2288，再返回照片1514×1006／row2272。每次几何参数都与原始setter写入后的寄存器一致，三对原生调用帧无缺失或无匹配返回；视频使用另一份core模板，而四个RAW地址继续复用。上游RAW格式字段一直为1514×1006／2272，因此不能将相同地址视为相同布局，或直接按新row读取旧RAW后宣布视频完成。

**本轮观察器整体判据未通过，CLI exit1。** 原厂窗口本身完成55.016客体秒并正常关闭；但分发函数共128次命中，超过每点100份payload预算，后28次payload未捕获，`completed_observation=false`保持原样。已捕获的三个完整配置包和三对几何调用有独立证据，不能由此声称整窗完整采样，也不能将此预算失败描述为原厂相机异常。

没有新QEMU内核或设备完成来源，没有修改r49恢复门槛。原严格双流水恢复仍false，视频、MAIN／WORK数值生产、原厂媒体及AF尚未验收。

## 1. 实现和身份

新增 [只读快照模块](../../tools/z62_paired_source_snapshot.py)、[原厂观察器](../../tools/trace_z62_paired_source.py)和[证据复核器](../../tools/verify_z62_paired_source_evidence.py)。它们记录配置分发前的参数、旧MMIO，以及几何setter完成两次STR之后、原POP之前的真实MMIO；不注入完成或修改客体状态。

复用冻结r53 EXE，SHA256 `68c33032d87c67cb4996950ea9fd3b15b9ced88b12924116696a289d99fb1581`，18层源、生成树、二进制及运行DLL身份复核通过。QEMU基线仍10.2.4，Windows x64。原master含CRC SHA256 `bb83613121f843d65101da936d942acdc513d86dbd3abc26259d0d870d03f5d4`，原始字节未改。

层级是A原厂执行和宿主只读取证；已有C级近似ISP继续作为背景实验配置。本阶段没有新物理ISP方程或新像素生产者。

| Z62 VA | 已核对行为 | 证据边界 |
|---|---|---|
| `102E750E` | 从根记录索引0取core，索引3取RAW source，索引9取输出包；按块是否为0选择重载 | 不是每次都发布整套新配置 |
| `102E8336` | 将68字节core的`+2C`传给几何setter | core中的其他字段分别由独立调用写入 |
| `1036C3B0` | 读取两个小端32位参数、旋转16位，写paired+44／48 | +48来自第二组半字，即width／height |
| `1036C3DC` | 两次STR已执行、尚未POP | R5／R6仍保存原对象／geometry指针，SP为入口SP−16；用于真实帧配对 |
| `1036C7BA` | 源包的四组地址写310／330／320／340，半字stride写30C | 几何返回时不能假定stride也已写完 |

实际初始9.778秒：dispatch前paired几何／stride均0；geometry返回后几何变1514×1006，但stride仍0。视频和返回照片同样分别记录新几何与后续独立跨度。观察器没有把顺序写入合成为一次原子提交。

根记录本轮只读取52词／208字节前缀，以覆盖索引0／3／9。随后读完分发函数尾部，发现还读取word52（+D0），而word51（+CC）和word52是独立标志。**不是完整53词配置，代码输出名`pointer_arguments`也不代表全部前缀词都是已识别指针。** 未读取的尾标志保持未知；旧运行源和旧回执不改。

## 4. 从包回溯到描述符

本阶段从自身实际root `C2379584`、对象基址 `C2379558`和目标ROM字面量重新定位，未沿用Z7II的地址。结果为：

- `102C1216`建立root各块指针，默认core在序列化区+0，source在+7C，outputs在+134。
- `102C0678`可将core直接指向frame-context+35C保存的模板，故core无需位于默认序列化区内。
- `102BFEBA`从frame-context+8开始的descriptor指针表逐项取DMA地址，字段为descriptor+34；source stride直接取第一个descriptor+26。
- `102C13D6`的一条构造路径从第一个descriptor+28／2A取几何；另有预制模板路径。不能把某一条路径的复制关系推广为所有模式均采用它。
- `102C1D98`／`102C1E1E`分别准备不同提交路径的参数，再写CC／D0标志。其调用链中存在模板绑定、调度和独立source布局，仍缺实际帧描述符以及输入生产者的交叉验证。

因此下一轮r57改观察序列化之前的carrier和完整53词root，验证视频的descriptor是否已经声明1516×854／2288、模板与实际输出块如何对应。这项新实验观察不同边界，不重跑旧点来使旧失败变绿。

Ghidra输出在`analysis/z62-ghidra/paired-source-r56-{dispatch,wrappers,builder,packets,origin,raw-layout}/`。每批manifest保留命令、原始SHA和结构审查；wrapper间接尾调用的jumptable告警、builder中的PIC和bad-instruction告警全部保留。部分在push之前有预备指令，单凭push定位的`102E8110／8124`不是已确认API入口；实际调用进一步指向`102E810A／811E`。本轮结论只使用已对原指令及实参核对的限定片段，不声称全部伪代码或函数边界正确。
