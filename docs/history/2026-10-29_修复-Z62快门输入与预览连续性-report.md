# Z62 快门输入与预览连续性

## 结论与范围

旧控制台将扩展器输入0标为“EXIT”，但这不是已确认的快门半按输入。同条件对照中，输入0使预览停在424批，外接半按G14则正常返回拍摄并持续到847批。无按键45秒对照也持续取景，因而不能用“默认30秒待机”解释此前停流。图像任务停止时立即返回空闲并发出两次停止通知，没有进入被怀疑的1000单位等待。

机身半按G1的第一次试验还暴露了独立问题：未显式释放G13会同时产生半按和全按位。r10b在启动前显式释放G1/G13，保留r10初次试验和失败边界。r10b已完成两轮纯半按菜单往返及持续预览验收，统一入口已切换到r9内核与r10b输入。

本报告是普通固件逆向与功能修复记录，`flavor=null`。授权与边界见 [scope](../../analysis/z62-isp-r10/scope.md)。固件是裸ARM/Thumb映像，无PE/ELF导入表；Ghidra仅分析选定函数，反编译不能替代指令和运行证据。完整ISP、拍照编码、保存回放、全部更新处理器和NOR更新仍未完成，不能据本次预览测试推断真机刷写安全。

## P1：原控制器调用链

`path_type=callflow`：

1. `0803DE84`将资源描述符写入`200184C8`指针表。
2. `0803DCFC`按ROM表`0804F01D`扫描六项输入；描述符9对应状态槽1，11对应槽2，12/13对应槽40/41。
3. `0803CE30`读取描述符`+8`的GPIO端口与`+C`掩码，查询端口`+10`输入寄存器；去抖极性为低有效。
4. 实测描述符9为PG1，11为PG13，12/13为PG14/15。固件仅在对应半按有效时保留全按状态，因此默认低电平的G13此前被掩盖。
5. `0803D70C`将槽1/2汇总到`200114E9/EA`，槽40/41到`20011551/52`。消息前缀占4字节。
6. 主引擎`10436600`将消息`+7/+8`解码为`80000000/40000000`；`+6F/+70`解码为`08000000/04000000`。

扩展器0走独立的汇总字段，最终到`C25D6FE6`，没有对应上述快门位。其真实物理用途和完整停流恢复协议仍未确认，本次没有替它改写固件状态或补造完成事件。

## 实现与检验

`tools/z62_shutter_input.py`提供宿主输入编号24，经既有150ms客体时间队列驱动PG1；数字24不是扩展器物理引脚。失焦、取消和关闭会释放该GPIO。原始输入0保留研究接口，不再作为新页面的返回拍摄按钮。

`tools/z62_shutter_input_v2.py`在CPU开始运行前驱动PG1、PG13为释放电平。`tools/run_z62_shutter_preview.py`是独立入口，沿用r9内核；状态额外报告`2026.10.29-input-r10b`及输入适配器散列。r9设备C源码和冻结构建未改。

最终全量267项回归通过，其中输入定向6项覆盖真实队列代码、启动释放顺序、短点击边沿、失焦取消、旧输入隔离和非法编号拒绝。`shutter-cycle-v2/report.json`记录两轮导航通过、全按位始终未出现、半按80000000实际出现及正常关闭：

完整复核命令：

```powershell
python -X utf8 -B tools/verify_z62_shutter_evidence.py
```

此命令要求`shutter-cycle-v2`两轮纯半按、每轮返回拍摄后持续至少5秒产生新预览，以及原版/候选和统一CMD的HTTP入口与释放验证。记录缺失或观察未完成会失败，不输出“完整相机”或“刷写安全”结论。摘要使用独立文件，保留升级前的`summary-before-entry.json`。
