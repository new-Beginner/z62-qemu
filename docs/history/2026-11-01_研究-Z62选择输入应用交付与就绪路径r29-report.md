# Z6II 选择输入应用交付与就绪路径 r29 研究报告

日期：2026-11-01。实现层级：A/B链路观察与宿主只读工具。完整目标继续active，当前仍优先任务一M5；没有修改或优化AF。

本轮确认持续选择输入的两个值都交付给原厂APPLV，变化标志也由原厂自然更新。此前OSD无法恢复的现象仍存在，可以排除本次MCU／主输入／应用交付丢失；具体切换策略和未完成的后端条件尚未最终确认。没有将pin0命名为照片／视频拨杆或把它直接接到C录像模式。

## 实际原厂交付证据

真实QEMU trace（本地证据，未分发：`analysis/z62-selector-r29/application-route-1/trace.json`）正常观察至**55.126客体秒／813.922观察宿主秒**，detach=OK、process_closed=true、exec53350 exit0；指定stage `z62-reference-jrflhb1s`无QEMU残留。结构化route（本地证据，未分发：`analysis/z62-selector-r29/application-route-1/route.json`）含16份相关断点快照。

| 阶段 | 拉低时的原厂结果 | 恢复高电平时的原厂结果 |
|---|---|---|
| 虚拟电平 | 30.667秒：FFFFFF→FFFFFE | 39.366秒：FFFFFE→FFFFFF |
| MCU解码前 `10436600` | 30.695秒，报文57=1，旧decoded仍0 | 39.383秒，报文57=0，旧decoded仍1 |
| 比较前 `1038D886` | decoded／当前缓存已1，前次缓存0 | decoded／当前缓存已0，前次缓存1 |
| 变化检查返回 `102A583C` | 返回1，标量为当前1／前次0／变化1 | 返回1，标量为当前0／前次1／变化1 |
| APPLV入口 `10540246` | 30.701秒，R0=`C1F7A5AC`，实际参数中也是1／0／1 | 39.386秒，同一参数地址，实际值也是0／1／1 |
| 后续自然处理 | 30.708秒，1／1／0 | 39.394秒，0／0／0 |

没有以解码前的旧值冒充新输入已处理，也没有把变化标志永久置位。应用输入从实际R0读取；先前资料中的R0签名与本次动态参数相符，没有假定它位于R1。GPIO只进行了计划内的两次切换，后续快照不是重发控制。

30.069秒的原厂摄影OSD存在；38.758秒低电平截图及47.477秒恢复后截图均无OSD且逐字节相同。结束时仍display_enabled=false、ready_join=1。因此观察完成和应用收到输入均不等于模式恢复完成。选择实验回执（本地证据，未分发：`analysis/z62-selector-r29/application-route-1/selector.json`）继续将物理身份／录像验收保留为false。

一次QMP只读超时发生于771.328宿主秒，之后同一会话继续到55.126客体秒，没有将超时当作退出或重发控制。4GiB卡snapshot前后原文件SHA仍为`27386955eeb28270fd04bf6e2ea9f6baa09f1235e11f5041dbb0a83dd8e61da7`；这不代表guest未写自己的快照。

## 策略与就绪路径的新锚点

本轮对原始master继续定点导出，SHA为`bb83613121f843d65101da936d942acdc513d86dbd3abc26259d0d870d03f5d4`（含成员CRC）。Ghidra输入是raw模块，无PE／ELF导入表；程序、原指令列表和manifest均保留。

| 原厂位置 | 当前证据与适用范围 |
|---|---|
| `1029AB9E→1029A9BA→103FD304` | 应用交付包装和间接回调；本次动态确实到达APPLV，但不以静态间接目标代替运行证据 |
| `1029FDEA` | 静态读取输入`+7C/+80`，构造ID3和0／1值，调用`1035CE6A`；不据ID3猜测实体名称 |
| `102A735C` | 静态把模式盘code转换为ID0的配置值，和上述ID3一起进入批量请求 |
| `102A0126` | 在4MiB范围检索到调用`1029FDEA`的BL候选；结果（本地证据，未分发：`analysis/z62-selector-r29/system-change-callers.json`）明确尚非运行命中证明 |
| `1035CE6A→103F7D9A` | 原始跳板及批量参数校验／请求路径；本轮未在该路径新增运行断点，不宣称请求被接受或完成 |
| `10321E20` | 既有导出存在按参数`+18`变化清除ready_join bit2的条件；这是待验证的本次清除来源 |
| `10322B50` | 既有原厂回调置ready_join bit2，满足3时继续上层就绪；需继续定位其注册、触发和未回调条件 |

`selector-system-change-r29-1`的两个新导出结构检查通过。`selector-policy-r29-1/103fd304.c`保留间接跳转告警；`selector-request-r29-1/10623930.c`有PIC告警，未作为完整切换策略规格。结构检查通过同样不等于硬件语义已验证。

“帧处理就绪未恢复”目前是下一条具体排查路径，不是已经证明的唯一根因。必须结合原厂写观察点、请求／回调及真实设备完成数据核对，不能直接设置ready_join、display_enabled或补造成功通知。
