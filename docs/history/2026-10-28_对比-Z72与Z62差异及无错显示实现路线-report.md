# Z72 与 Z62 QEMU：差异、资料缺口及无错显示实现路线

> 日期：2026-10-28；普通固件/模拟器分析，flavor=null。**本轮为分析与规划，不是设备修复交付。**

## 结论

Z62 不需要重新做一套菜单显示：它已能运行原厂 C1.70、输出 1024×682 菜单并响应控制器按键。本地参考版也不是只搬了 Z72 的菜单，既有覆盖记录显示已纳入 Z62 上游全部30个 C/头文件。需要继续解决的是**型号相关的采集停止、完成确认及重启协议**。

“像 Z72 一样”必须分成三层：①原厂菜单稳定可操作；②返回拍摄应用没有致命 Error 对话框；③能再次打开 MENU。Z72 上游曾做到②而仍未做到③，因此不能把消框当成内部错误状态或采集会话已修好。当前 Z72 实例的只读画面确实没有致命对话框，但本轮没有再发送第二次 MENU。

**建议先达成①②，再单独攻③；真实取景和拍照另立阶段。** 不通过清除 DSID、强制应用索引、改返回值或覆盖帧缓冲来达标。

### 1.2 为什么 Z72 不弹框，不代表第二次 MENU 已好

Z72上游的独立研究记录说明：启用采样源和计数后，一次菜单退出不再显示致命对话框，但当时 `0x3F` 仍在，重开仍受采集会话/门控约束。拍摄应用重启、错误框绘制、MENU许可不是同一个条件。

依据：Z72错误显示研究（本地证据，未分发：`<WORKSPACE>/.build/z72-latest-4a7bed3-upstream/research/z7ii/error_display.md:64`）。这是上游历史运行条件下的记录，不是本轮新测出的所有最新实例行为。

本轮只读观察到：Z72 `execution=running`、`index=3`、`menu_inhibited=false`，当前 OSD画面（本地证据，未分发：`<WORKSPACE>/artifacts/z72-z62-comparison-2026-10-28/z72-current.png`） 没有致命对话框。该时间点不证明完整停止/重启协议正常，也不证明第二次MENU成功。黑色背景不是有效传感器图像。

### 1.3 Z62 已定位到什么程度

已有本机只读断点证据，而非仅凭相似性猜测：

1. `102DBB9C` 的入口参数为1，返回值为 `0x180`。
2. 第一等待返回0，形成错误位 `0x80`；模式停止等待形成 `0x100`；其余被观察的清理调用返回0。
3. 通知分发处观测事件9及 `R4=0x180`；随后状态追加处 `R0=0x3F`。
4. 已有完成源组合下再次MENU仍命中 `106231C2`，`R4=0x24`、谓词返回1、列表含63。按键到达了固件，但许可被拒绝。

| 失败位 | 等待的软件事件 | 由原厂代码确认的完成通知路径 | 仍未知 |
|---|---|---|---|
| `0x80` | `0x800`，等待参数100 | IRQ92 bit1，状态/掩码 `20065508/2006550C`；回调设置事件 | 本轮对应请求何时应完成、原因是否锁存/被消费、内核原始失败码 |
| `0x100` | `0x20`，等待参数150 | mode0相关，sync组2 bit10，状态/掩码 `20060044/20060040`；回调设置事件 | 提交/武装/取消/确认的正确顺序，以及后续重新起流条件 |

100/150是原指令传入参数，时间单位未核定；等待包装器折叠错误码，不能仅凭返回0断言就是超时。软件事件位也不能直接等同硬件IRQ位。

依据：[较新诊断结论](2026-10-27_逆向-Z62致命错误与取景缺口-report.md#L102)、原始等待指令（本地证据，未分发：`<WORKSPACE>/analysis/z62-capture-diagnosis/stop-wait-disassembly.txt:2`）。

### 1.4 已试过但不能当修复的方案

- sampling-source开/关：两组均完成初次菜单与退出，`reopened_menu=false`；既有截图均记录致命Error。
- frame-start + sensor frame/mode completion：曾有无Error框的OSD截图，但后续重新出现63且不能重开。
- 再增加metadata、input-command、init completion及初始化延迟：仍没有通过菜单循环。
- 以上不是“缺少开关入口”；也没有证明应周期广播所有完成事件。时序过早、事件被清除、请求取消、错误重建及其他路径尚需区分。

注意：`/status.error=null`只表示控制台没有记录宿主异常。Z62在致命Error画面时也可能仍是running/error=null，验收必须同时检查原始帧和固件状态。

## 2. 真正缺失的资料

| 优先级 | 缺失内容 | 为什么重要 | 最小获取方式 |

## 3. 如何实现：分阶段最小路线

### 阶段A：先建立可比较的基线

- 保留旧v0.4严格探针与参考环境，不混用；固定两机型提交、EXE哈希、启动选项和参数组身份。
- 统一观测适配层：前台应用、客体时间、LCD/输出有效性、帧、按键队列和固件错误状态。Z72没有的status字段应通过可验证只读接口补齐或改判据，不默认当false。
- 同样记录首次MENU、DOWN、EXIT、第二次MENU；每个阶段既要原始帧，也要状态。不能用索引1代替完整菜单绘制。
- 对照卡状态、主屏实验、采样源和捕获边界；默认不带两次外部raw103实验注入。

**产出：**统一阶段报告、配置清单和逐帧证据。未通过的菜单循环必须返回失败，不能只检查初次menu_ready。

### 阶段B：针对已知失败点补最小设备合同

1. 优先恢复 `0x800`、`0x20` 两类等待的完整生产/消费时间线，明确每次设备完成对应的请求编号/代次。
2. 若证据证明设备缺响应，按“提交→武装→完成→锁存IRQ→W1C→取消/复位”建模；屏蔽时保留状态、取消后不误完成、每个请求只完成一次，主从隔离。
3. 采样结果仅在命令/模式允许时更新，读回值要符合Z62消费者；不以任意递增计数替代未知结果结构。
4. 将 `20061000` 重臂视为单独受控候选：先证明对应Z62命令和使能条件，再实现；不要按墙上时间无条件写FFFF，也不要只为界面好看恢复所有位。
5. 对已存在的完成源先验证时序和消费，不再笼统全部开启。若等待确实依赖数据处理，恢复最小必要的数据合同，而不是伪造软件成功消息。

**视觉里程碑（Z72同级）：**初次原厂菜单稳定可导航，退出后在约定客体观察窗口不出现致命Error。Card/Err存储提示和0x3F状态必须另报；有0x3F时不能命名为“内部错误全部修复”。

**设备正确性门槛：**两个等待按正确路径成功，停止函数不再累积0x180，无错误重建；以去掉断点/外部边界注入后的复验为准。这是拟定验收，不是本轮已通过。

### 阶段C：独立完成第二次及重复MENU

- 追踪停止完成、采集会话释放、结果排空、重新初始化和错误状态自然移除的完整生命周期。
- Z62已有许可表拒绝证据，因此先让设备协议自然满足许可，不改gate或DSID。内部错误消除后若仍失败，再检查延迟MENU请求和应用切换的下一条件。
- 加入多次冷启动和连续循环验收；建议先以10轮冷启动、20轮MENU/EXIT循环作为初始回归标准，再按发现扩充。两者都是计划目标，不是现有结果。
- 验证任务真正被调度：旧调用栈不代表仍在等待。上游已修过Z62一次性定时器IRQ176饥饿，不应把这项已带入的修复重复当缺失代码。

### 阶段D：真实取景、拍照和存储另行验收

仅在状态机基线可信后推进：可审计像素源→Bayer DMA→实际后端节点→LCD视频层；再做曝光/编码/保存。测试图案只能证明模拟成像链，黑色或绿色背景、剩余张数、SD挂载都不是拍照成功。
