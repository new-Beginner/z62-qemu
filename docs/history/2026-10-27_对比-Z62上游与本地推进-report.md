# Nikon Z62 上游与本地 QEMU 对比及推进

## 结论

用户提供的 https://github.com/xiaoqingfeng0526/nikon-z62-qemu 已实现原始菜单、控制器交互、部分拍摄OSD及存储/采集设备合同。它不是没有功能的骨架。本次 fetch 与 ls-remote 确认默认分支为 `z62-r3`，HEAD 为 `4f4389944fc339d107f22f5f7ca3f90cc34b78de`，与本地固定子模块相同，新增提交为0。

本地有两套不同环境：旧v0.4是严格无界面启动探针；目前可操作菜单的原生参考环境已使用该上游的完整准备流程。生成树中的上游30个C/头文件全部存在，28个逐字节相同；`nikon-z72.c` 与 `nikon-z72-controller-i2c.c` 是已知Windows兼容/输入追踪/肩屏适配。不能把旧探针的限制误认为当前参考构建的遗漏。

本轮补齐本地包装器未开放的SD镜像入口，宿主版本推进至 `2026.10.27-r2`。设备二进制仍为r1，没有重编译、修改客体或宣称修复Error。没有安装包发布，也没有提交或推送。

## 能力矩阵

| 环节 | 旧v0.4 | 上游R3及本地参考版 | 仍缺什么 |
|---|---|---|---|
| 启动 | 局部RAM/MMIO、严格遇未知停止 | 主/从/控制器原始固件组合、参数组、菜单启动 | 完整拍摄状态机验收；真实校准 |
| 双机 | 两个独立探针进程，无双芯片通信 | 分离地址空间、共享消息RAM、远端窗口、握手 | 不能据此宣称所有外设交互完整 |
| 控制器 | 无控制MCU仿真 | Cortex-M4、GPIO/I2C/SPI/DMA/ADC/电池等模型 | 实验响应并非硅片全合同 |
| 显示 | 无LCD/MENU | Z62 LCD、Y/UV与overlay合成、图形设备、原始菜单 | 有效取景像素；肩屏物理段码 |
| 输入 | 无原厂菜单按键路径 | 控制器去抖、MENU/EXIT/方向键、网页显示终端 | 菜单重开状态机仍阻塞，不是简单按键遗漏 |
| 存储 | 无SD模型 | SDHCI/从侧SD卡总线、快照镜像；上游已有4GiB SDHC/FAT32挂载证据 | 本轮仅实测卡接入；照片保存仍未验收 |
| 传感器 | 无 | 配置、状态、IRQ、初始化/模式/帧完成实验源 | 实际像素源、Bayer DMA |
| ISP | 无 | 部分控制、图形/内存操作合同 | 完整11节点成像后端及编码/保存链 |

源码锚点：`qemu/nikon-z6ii.c`的旧板限制；`tools/build_reference_qemu.py`的完整prepare与来源验证；`third_party/z62-qemu/qemu/prepare_source.py`设备清单；`qemu/nikon-z72.c`双引擎与控制器连接；`qemu/nikon-z62-sensor-config.c`明确说明不产生像素/DMA；`README.zh-CN.md`与`docs/z62-port.md`的功能验收边界。此处后四个相对路径均指上游子模块内文件。

## 已实施：SD镜像入口与版本记录

- `tools/run_reference_console.py`新增 `--sd-card` 与 `--version`；默认无卡行为不变。
- 只接受存在的普通文件、正的512字节倍数，拒绝非ASCII/含逗号路径及Z72使用该参数。逗号拒绝避免QEMU `-drive` 选项注入；不是文件系统/容量合法性认证。
- 透传原上游SD入口，不重写SD模型。上游强制 `format=raw,snapshot=on`，卡接到 `/z72-sd-slave/sd-bus`。
- 会话记录宿主版本、卡路径/大小、快照写入和未验收文件系统状态。
- 新入口 `start-z6ii-reference-2026.10.27-r2.cmd` 明示“宿主r2 / 设备r1”，保留旧入口与EXE。r1构建清单哈希校验继续有效。
- 不开放已失败的握手组合作为默认功能；`main_screen_experiment=false`、`experimental_boundaries=0`。

运行方法见 [README-MENU](../profiles/README-MENU.md)。若需要卡内文件，提供自行合法取得的raw镜像；本入口不会自动创建或格式化镜像。客体写入不持久化到原文件，不能用它验收持久照片保存。

## 验证

1. 新增5项SD入口测试：默认无卡、文件保持、非法路径/大小/机型拒绝、参数透传与会话记录、错误在staging前终止。初次测试夹具遗漏既有parameters字段，补齐后通过。
2. `python -m unittest discover -s tests -p 'test_reference*.py' -v`：38项通过。
3. `Z6II_QEMU_REQUIRED=1 python -m unittest discover -s tests -v`：101项通过、零跳过，62.546秒。
4. 原生r1 EXE＋r2入口＋64MiB空白测试卡，在独立8668端口启动；检查运行状态、从侧SD设备、有效snapshot参数、r2会话记录。通过上游 `/stop` 正常关闭，确认端口关闭。
5. 测试卡启动前、运行时、停止后SHA256均为 `3b6a07d0d404fab4e23b6d34bc6696a6a312dd92821332385e5af7c01c421351`。该卡未格式化，未声称挂载或客体写入已验证。
6. 新CMD实际执行`--help`，固件准备检查和命令帮助成功退出，显示r2及SD选项。

## 后续推进顺序与未解决事项

1. 当前Error/重开问题不是缺少上游新代码。此前已捕获停止函数的两类等待失败；已有完成源组合仍未通过循环，应先修复追踪覆盖、核实事件与消费时序，再补设备行为。详见 [诊断报告](2026-10-27_逆向-Z62致命错误与取景缺口-report.md)。本轮没有重跑或宣称解决该缺陷。
2. 存储下一验收点是已知布局的4GiB FAT32测试镜像在本机自然挂载；本轮只完成入口和接入验证，不用“有卡”替代挂载与写入证明。
3. 图像下一验收点是像素输入→DMA缓冲→后端节点→LCD有效帧；不再把增加ready/完成事件视为取景实现。
4. 普通旧参考二进制缺少新版manifest。防串版校验值得做，但本轮不强制引入以免破坏旧入口；后续需先为旧构建建立可靠来源记录，不能凭当前文件哈希自我认证。

当前阻塞仍是采集握手/状态时序及未实现像素/ISP管线，不能由重新拉取同一上游或启用SD卡直接解决。
