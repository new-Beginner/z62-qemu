## 实际调用链的验证

stack-contract（本地证据，未分发：`analysis/z62-selector-r37/stack-contract.json`）同时保存原始指令窗口和70条匹配序号。这里没有通过“栈中出现某个地址”猜调用链，而是核对：

1. 列表移除助手1034C026仅push R4／R5／R6／LR，16字节，无额外局部栈；计数写点SP+0xC因此是该助手保存的返回LR。
2. 70次减一的SP+0xC均为103D335B，对应原始103D3356的BL 1034C026，返回PC103D335A及Thumb位。
3. 所在回调103D32EE的原始序言push六个寄存器，共24字节，无额外局部栈；它的保存LR位于计数写点SP+16+20，即+0x24。
4. 70次该位置均为10295579，对应10295576的BLX R2返回。
5. 原始10295558线程循环从对象+0x20读取FIFO，随后取对象+0x24登记回调，传对象与取出的包调用；新的该函数导出无列出结构问题。

因此，本次70条记录可限定为：

```text
10295558 完成工作线程 → 10295576 间接调用
    → 103D32EE 回调 → 103D3356 列表移除
        → 1034C026 → 1034C05C 原生计数减一
```

CPU线程、实际SP、寄存器和保存字均保留。这不是通用栈展开器，也不把线程循环的FIFO等待当成已证明的1秒原因。

回调原指令还显示：先清工作记录+3E30的一个标志，再在剩余标志非零时以参数5调用等待／让出辅助；之后才移除列表。移除后，在子系统状态3／4／6时检查三个列表和停止标志，满足后可由103D3424请求0x2000工作。此处的轮询时长、是否经过以及完成FIFO的上游供给时机，当前都没有在同一个请求内测量；不能仅凭约1秒间隔选择其中某一项为根因。
