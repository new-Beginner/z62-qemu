# Z62 处理前缀拒绝与状态4门控 r34

日期：2026-11-02。本阶段增加独立只读完成条件观察器，未发布新QEMU内核。完整55秒实验定位到一个实际执行的拒绝条件：切换后操作码与子系统记录的模式均为29，但子系统状态为4，原厂函数只接受1或2。原厂显示恢复仍未通过，状态4的来源和自然恢复路径继续由独立写观察核对。

## 范围与新实现

[scope](../../analysis/z62-selector-r34/scope.md)限定离线QEMU、专用snapshot卡和原始C1.70。原厂指令与执行属于A；RAW边界／连续统计为既有B／C模型；新程序属于宿主只读观测，不把控制状态数值命名为真实CPU或DSP状态。

新增`tools/trace_z62_selector_completion.py`，对六个精确原指令位置设置断点。解析C1868A70上下文、C1864CD0状态字、C23DC970带符号计数，以及已证实操作对象+0D、+144载荷指针与载荷+2CCE；不写这些字段。替代构造入口1032286E没有已证实的R4操作对象布局，因此不追读R4。返回值始终保留整数。

4项新测试先失败后通过，覆盖字段／指针分离、带符号计数、入口旧R0不当返回值、构造输入不当对象，以及短读和越界。原始固件身份和六个断点的原字节在运行前核对。

## 对照原指令后的解释

新的103D3464导出（本地证据，未分发：`analysis/z62-ghidra/selector-completion-r34-1/103d3464.c`）和10327896导出（本地证据，未分发：`analysis/z62-ghidra/selector-completion-r34-1/10327896.c`）结构检查没有列出问题；原始master哈希未变。前者明确先拒绝操作+0D与C1864CD2不同，或C1864CD1不是1／2。本次608次落在状态4条件，不能通过宿主把4改成1来“修复”。

函数还含部分模式下的通道就绪检查与后续请求入队。它的非零返回也不等于像素处理完成或设备ACK。103226D0导出仍有PIC／BADSPACEBASE问题，不作为完整规格；只保留先前已由原指令确认的局部事实。

重新阅读已有准备帧函数103215BC（本地证据，未分发：`analysis/z62-ghidra/ready-frame-prepare-r12/103215bc.c`）及原指令，还确认了一条此前短窗口扫描未覆盖的code16来源：10321CD4检查R10；内部标志非零，或10321CE6调用103D3464后非零，都可到10321CEC；状态8时10321CF4／CF6将16写入本函数返回槽。该路径解释了为何不能仅盯两个直接构造16的调用点。当前没有把初始化r33的那次16动态归属到此路径。

103D3464中另一个只适用于部分模式的就绪函数10273F26，经10273EA2选择RAM通道对象，再由102E127C要求+4／+14非零。原表中通道1对象C26AD4F0，通道2对象C26AD508。当前实际操作码29已在更前面的状态检查被拒，未据此认定这两组通道字段就是本次缺失条件。
