# Z62 软件录像与混合媒体卡 r26b 阶段报告

本阶段实际实现“软件视频模式→同源已消费帧连续采集→录像键开始／停止→宿主H.264编码→MP4／封面成组存卡→视频播放／导出→删除”。已在原版与原包走候选分支的真实QEMU会话中验收，浏览器完成203帧、7.479354秒样本的播放，独立导出逐帧核对来源及有损编码误差。

这是C级替代路径，默认640×424、可变帧间隔、无音频。没有执行原厂视频编码器，不代表全分辨率采集、原厂照片／视频拨杆、原厂镜头或AF、完整更新及断电恢复。QEMU设备继续使用冻结r24，SHA256 `dbe36d222dbfa633086f906f626968635c61d9825eaee8174480bef22a39abf2`；软件版本为`2026.11.01-video-console-r26b`。

网页样本192,499字节，SHA256为`bf8372f8bd606be45da9fa0662094a99779f729efb7777dcd44f00957f896021`。浏览器实际640×424、readyState4、ended=true、无解码错误。删除MP4及封面后主进程exit0，卡重开为空；五个实际运行媒体模块与当前源逐字节相同，见网页验收记录（本地证据，未分发：`analysis/z62-video-r26/ui-qa-compat.json`）。

源RGB与解码RGB不再要求字节相等，因为4:2:0色度采样和CRF18是有损处理。原始源哈希、RAW标签与时间序列仍严格核对，编码后帧哈希另行记录，逐帧MSE独立核对。当前1000的MSE拒绝上限是实验验证策略，不是尼康画质指标；实际样本最大误差约3～4。若外部高频彩色场景超过上限，工具会拒绝提交，不伪装成功。

## 发现并修复的边界

1. 停止与最后源采样恰在同一时刻时，该帧没有正持续时间。新增回归先失败，再实现排他停止边界，并让状态帧数与实际编码帧数一致。
2. 初版r26的RGB无损MP4经FFmpeg逐像素一致，浏览器能播放到结尾且无解码错误，但视觉截图出现紫绿偏色。该结果不能作为正确浏览器回放验收。保留原始239帧存档（本地证据，未分发：`analysis/z62-video-r26/ui-export-1/export.json`）、原版／候选记录与旧回归，修正为r26b通用H.264/yuv420p后重新执行专项、实际QEMU、候选、浏览器颜色和全量测试；没有只弱化旧哈希断言来掩盖问题。
3. 普通面板操作结束会重新启用全部按钮，曾让未录制状态的停止键短暂可点。r26b在统一操作完成后按真实视频状态重新渲染可用性，并在刷新时纳入busy状态。
4. 旧RGB网页重启对照实际保留了原视频；同一v3卡又生成`Z62_0002.JPG/NEF`，删除照片组后旧视频仍在。补充拍照第一次在前置QMP读取超时处被拒绝，接点计数和事件记录均为零；确认未发出按键、读取恢复后才进行新的拍照测试，未补造照片或重发未知控制操作。

## 测试与剩余问题

视频新增24项专项通过。修正版全量 **415项通过，176.038秒，零失败、错误和跳过**，使用隔离视频Python，见结果摘要（本地证据，未分发：`analysis/z62-video-r26/regression-compat.json`）。旧RGB版415项／148.716秒保留为历史范围，不代表颜色兼容性已通过。没有PyAV的普通Python会明确跳过视频专项，不能把那种结果称为视频验收。

当前较长片段的编码／审计仍在输入线程持锁执行，可能导致HTTP／QMP读取超时及连接中止。读取恢复与最终文件正确不等于交互流畅或长稳通过。下一步应将编码完成改为可观测的异步状态，并完善请求、关闭和就绪提示；这没有在本阶段宣称修好。

原厂视频／照片编码、音频、全分辨率传感器、照片视频与电源拨杆、触屏／肩屏完整行为、原厂镜头／曝光／SD播放器互通、整机快照恢复和任务二原厂AF仍未完成。该软件录像不能证明任意候选固件的原厂录像正确，更不能证明真机刷写安全。
